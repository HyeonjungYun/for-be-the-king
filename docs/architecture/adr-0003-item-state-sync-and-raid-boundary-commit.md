## Summary

던전 내 아이템 조작(착용·해제·루팅)을 매번 DB에 영속화할지, 아니면 런이 끝날 때
한 번에 커밋할지를 정한다. **레이드 경계 커밋**을 택한다 — 던전 내 변경은 Room 메모리에만
반영하고, DB 쓰기는 **탈출 성공 · 사망** 두 지점에서만 일어난다. 멱등은 경로별로 갈라
던전 내 요청은 세션 인메모리 `request_id` 집합으로, 베이스캠프 DB 직행 요청은 기존
`reward_grants` PK 패턴으로 판정한다.

## Context

### Problem Statement

`design/gdd/item-equipment-system.md`가 완성됐으나 **이 문서가 낳아야 할 서버 산출물이
현재 0이다** (`/design-review` 2026-09-03, network-programmer). `.proto`에 아이템 메시지가
없고, `Player`에 인벤·장비 필드가 없으며, 아이템 테이블도 없다.

스키마를 짜기 전에 **"아이템 상태가 언제 DB에 쓰이는가"** 를 정해야 한다. 이 답이
테이블 구조·패킷 왕복·실패 처리 전부를 결정하기 때문이다.

**지금 정하지 않으면**: P2(09-22 착수) 구현이 이 질문에 부딪혀 멈춘다. 나중에 뒤집으면
스키마와 패킷을 다시 짜야 한다.

### Current State

```cpp
// GDBQueue.Push 호출 지점 — 전 서버에 정확히 3곳, 전부 편도
Room.cpp                Room::SavePlayer      (퇴장·주기 저장)
ServerPacketHandler.cpp Handle_C_LOGIN        (토큰 검증 + 캐릭터 로드)
ServerPacketHandler.cpp Handle_C_GRANT_REWARD (지급 트랜잭션)
```

**DB 스레드에서 Room 으로 되튕기는 배선이 없다.** `room->DoAsync(...)` 호출은 전부
IOCP 워커에서 나가며, DB 작업 완료 후 게임 스레드에 결과를 반영하는 경로는 존재하지 않는다.

지급 트랜잭션(`Handle_C_GRANT_REWARD`)은 **DB 우선**이다 — 커밋이 끝난 뒤에 응답한다.
그래서 "응답은 성공인데 DB엔 없다"는 창이 애초에 없었다.

### Constraints

- **DB 스레드는 4개** (`GDBQueue`). 던전 내 조작마다 DB를 치면 120 동접에서 큐가 쌓인다
- **Room JobQueue는 단일 직렬 실행**이다. 여기서 DB를 기다리면 그 층 전체가 멈춘다
- **응답 지연이 전투에 직결된다.** 착용 요청에 DB 왕복(수 ms)을 넣으면 그 시간 동안
  플레이어가 옛 스탯으로 싸운다
- `technical-preferences.md` § 작업 소유권 경계 — 서버 구현은 사용자 영역이다.
  이 ADR은 결정만 하고 코드를 쓰지 않는다

### Requirements

- 착용·루팅 응답이 **DB 왕복 없이** 나가야 한다 (전투 스탯 즉시 반영)
- 같은 요청이 두 번 도착해도 **한 번만 반영**되어야 한다 (재접속 재전송)
- 서버 크래시 시 아이템이 **복제되지 않아야** 한다
- 손실이 발생한다면 **플레이어가 무엇을 잃었는지 알 수 있어야** 한다

## Decision

### 던전 내 아이템 변경은 영속화하지 않는다. 커밋은 레이드 경계에서 한 번이다.

**익스트랙션 장르에는 이미 자연스러운 트랜잭션 경계가 있다 — 런 그 자체다.**

```
던전 입장       DB → 메모리 적재 (인벤·장비 로드)
던전 내 조작    메모리만. DB 접근 0회
                (착용 · 해제 · 루팅 · 버리기 · 가방 열기)
탈출 성공       DB 트랜잭션 1회 — 인벤 확정
사망            DB 트랜잭션 1회 — 레벨 초기화 + 가방 생성 (ADR-0005)
서버 크래시     그 런 무효. 플레이어는 입장 전 상태로 복귀
```

### Architecture

```
                    ┌─────────────────────────────────────┐
   C_EQUIP          │  Room JobQueue (단일 직렬)          │
   C_LOOT     ──────▶  ① 메모리 반영                      │
   C_DROP           │  ② 세션 인메모리 멱등 집합에 기록    │──▶ S_* 응답
                    │  ③ DB 접근 없음                     │    (즉시)
                    └─────────────────────────────────────┘
                                    │
                        탈출 · 사망 시에만
                                    ▼
                    ┌─────────────────────────────────────┐
                    │  GDBQueue (전용 스레드 4개)          │
                    │  트랜잭션 1회                        │
                    └─────────────┬───────────────────────┘
                                  │ room->DoAsync(콜백)   ← 신규 배선
                                  ▼
                    ┌─────────────────────────────────────┐
                    │  Room — 결과 반영 · 브로드캐스트      │
                    └─────────────────────────────────────┘

베이스캠프 (Room 없음, ADR-0005 S5)
   C_STASH  ──────▶  GDBQueue 직행 — 실시간 전투가 없으므로 메모리 우선이 불필요
                     멱등은 reward_grants PK 패턴 재사용
```

### Key Interfaces

```cpp
// ── 세션 인메모리 멱등 ─────────────────────────────────────
// GameSession 에 추가. 던전 내 요청 전용이다.
// DB PK 패턴은 DB-선행 모델이라 메모리 우선과 양립하지 않는다.
class GameSession
{
    USE_LOCK;
    unordered_set<string> _handledRequests;   // 세션 종료 시 통째로 폐기

    // 이미 처리한 요청이면 false. 처음이면 등록하고 true
    bool TryBeginRequest(const string& requestId);
};

// ── DB → Room 콜백 배선 ────────────────────────────────────
// GDBQueue 작업이 RoomRef 를 캡처해 끝에서 되튕긴다.
// GRooms[FLOOR_COUNT] 는 전역 정적이므로 Room 이 먼저 죽는 일이 없다.
GDBQueue.Push([room, playerId, snapshot](DBConnection* conn)
{
    const bool ok = CommitRaidResult(conn, snapshot);
    room->DoAsync(&Room::OnRaidCommitted, playerId, ok);   // ← 신규
});
```

### Implementation Guidelines

**던전 입장 시 적재 시점**: `Handle_C_ENTER_GAME`이 이미 `characters` 행을 읽어
`Player`를 만든다. 인벤·장비도 **같은 조회에서 함께 읽어** Room에 넣는다 — 별도 왕복을
만들지 않는다.

**커밋 스냅샷은 값으로 복사한다.** 기존 `Room::SavePlayer`가 이미 그렇게 한다 —
람다가 `PlayerRef`를 잡으면 DB 스레드가 게임 스레드와 동시에 `posInfo`를 읽는다.
아이템 목록도 같은 규칙을 따른다.

**멱등 집합은 세션 수명과 같다.** 재접속하면 비어 있고, 그건 옳다 — 재접속 시점엔
그 런이 이미 끝났거나(탈출·사망) 진행 중이며, 진행 중이면 서버 메모리에 실제 상태가 있다.

**크래시 복구는 "복구하지 않는 것"이다.** 던전 내 상태를 DB에 안 쓰므로, 재시작 후
플레이어는 입장 전 상태로 돌아간다. 별도 복구 코드가 필요 없다.

## Alternatives Considered

### Alternative 1: 조작마다 비동기 영속화 + 실패 테이블

- **Description**: 착용·루팅마다 `GDBQueue.Push`로 DB에 쓰고, 실패하면 N회 재시도한 뒤
  실패 테이블에 적재한다. 부팅 시 그 테이블을 재생한다.
- **Pros**: 크래시 시 손실 폭이 작다 (마지막 성공한 조작까지 남는다)
- **Cons**: **응답을 먼저 보내고 DB는 나중**이므로 "성공했다고 본 것이 사라지는" 창이
  구조적으로 존재한다. 실패 테이블·재시도 정책·부팅 재생 코드가 전부 새로 필요하다.
  120 동접에서 루팅마다 DB를 치면 스레드 4개에 부하가 몰린다.
- **Estimated Effort**: 채택안의 2~3배 (재시도·실패 테이블·재생 경로)
- **Rejection Reason**: **부분 손실은 플레이어가 무엇을 잃었는지 모른다.** 런 무효는
  "아까 그 판이 날아갔다"로 명확하다. 그리고 이 장르 플레이어에게 후자는 이미 익숙한
  계약이다 — 익스트랙션 게임에서 레이드 도중 서버 크래시는 통상 그 레이드를 무효화한다.

### Alternative 2: DB 우선 (지급 트랜잭션과 같은 모델)

- **Description**: 착용·루팅 요청을 받으면 DB 커밋 후에 응답한다. `Handle_C_GRANT_REWARD`와
  같은 패턴.
- **Pros**: 손실 창이 없다. 기존 패턴을 그대로 재사용한다
- **Cons**: **착용 응답에 DB 왕복(수 ms)이 들어간다.** 그 사이 플레이어는 옛 스탯으로
  싸운다. `Room` JobQueue가 단일 직렬이라 DB를 기다리면 그 층 전체가 멈춘다
- **Estimated Effort**: 채택안보다 적다 (기존 패턴 재사용)
- **Rejection Reason**: **전투 반응성이 이 게임의 핵심**이다. 30초 교전에서 착용 반영이
  수 ms 밀리는 것은 받아들일 수 있으나, Room 직렬 큐가 그동안 막히는 것은 다른 29명에게
  영향을 준다.

### Alternative 3: 레이드 경계 + 주기 스냅샷

- **Description**: 기본은 레이드 경계 커밋이되, N분마다 인벤 스냅샷을 남겨 크래시 손실
  폭을 줄인다.
- **Pros**: 크래시 손실이 최대 N분
- **Cons**: **"어느 시점으로 되돌리나"라는 새 문제**가 생긴다. 스냅샷 이후 주운 아이템은
  사라지고, 스냅샷 이후 잃은 아이템은 되살아난다 — 플레이어가 그 경계를 알 수 없다.
  가방 루팅과 얽히면 **한 아이템이 두 사람에게 존재**할 수 있다
- **Estimated Effort**: 채택안 + 스냅샷 스케줄러
- **Rejection Reason**: 복제 위험이 손실 위험보다 나쁘다. 익스트랙션 경제에서 아이템
  복제는 시스템 전체를 무너뜨린다.

## Consequences

### Positive

- **DB 부하가 급감한다.** 던전 내 조작이 DB를 전혀 치지 않는다 — 루팅이 잦은 파밍
  구간에서 특히 크다
- **실패 테이블·재시도 정책·부팅 재생 코드가 통째로 불필요**해진다
- 착용·루팅 응답이 **Room JobQueue 안에서 끝난다** (수 μs)
- 크래시 시 결과가 **명확하다** — 부분 손실이 아니라 런 무효
- **복제가 구조적으로 어렵다.** 던전 내 상태가 DB에 없으므로 "DB엔 있는데 메모리엔 없는"
  불일치가 생기지 않는다

### Negative

- **크래시 시 그 런의 파밍이 통째로 사라진다.** 최대 30분 × 그 층 인원
- 서버 재시작이 **플레이어에게 비용**이 된다 — 배포 시점을 고를 필요가 생긴다
- 던전 내 조작이 DB에 없으므로 **운영 도구로 실시간 인벤을 볼 수 없다** (서버 메모리에만 있음)

### Neutral

- 멱등 판정이 **경로마다 다르다** — 던전 내는 인메모리, 베이스캠프는 DB PK.
  일관성은 떨어지지만 각 경로의 커밋 모델에 맞는 방식이다
- `Room::SavePlayer`의 주기 저장(60초)은 **위치·HP 전용으로 남는다.** 아이템은 이 경로를
  타지 않는다

## Risks

| Risk | Probability | Impact | Mitigation |
|------|------------|--------|-----------|
| 크래시로 다수 플레이어의 런이 무효 | 낮음 (CI·테스트로 안정성 확보 중) | 높음 (플레이어 불만) | 배포는 저활성 시간대. 크래시 시 안내 메시지 |
| 인메모리 멱등 집합이 장시간 세션에서 비대 | 낮음 (런 30분 상한) | 낮음 | 세션 종료 시 폐기. 필요하면 상한 도입 |
| 탈출 커밋 실패 (DB 장애) | 낮음 | **높음 — 탈출했는데 못 가져감** | **무한 재시도 + 탈출 지점 무적 대기.** 아래 § 탈출 커밋 실패 |
| DB 장기 장애 시 탈출자가 누적 | 낮음 | 중간 (대기 인원이 Room 에 남음) | 무적 상태라 전투에 영향 없음. 층 인원 카운트에는 잡힘 |
| 콜백이 이미 퇴장한 플레이어를 참조 | 중간 | 낮음 | `Room::OnRaidCommitted`가 `objectId`로 재조회. 없으면 무시 |

### 🔴 탈출 커밋 실패 — 이 결정의 유일한 진짜 약점

던전 내 손실은 "런 무효"로 설명된다. 그런데 **탈출에 성공했는데 커밋이 실패하면**
플레이어는 성공했다고 보고 결과를 잃는다 — 여기엔 그 설명이 통하지 않는다.

**결정: 탈출 연출 중 대기 · 무한 재시도** `[2026-09-04]`

```
탈출 게이지 완료
   ↓
커밋 시도  ──실패──▶  재시도 (백오프)  ──┐
   │                        ▲            │
   │                        └────────────┘
   │ 성공                 그동안 플레이어는
   ▼                      탈출 지점에 무적으로 대기
베이스캠프 전환            (연출이 계속 재생된다)
```

- **플레이어를 베이스캠프로 먼저 보내지 않는다.** 보낸 뒤 되돌리는 것이 가장 나쁘다
- 대기 중에는 **무적**이다. 커밋을 기다리는 동안 죽으면 사망 처리와 충돌한다
- **탈출을 취소하지 않는다.** 30분 타이머가 도는 게임에서 "탈출 실패, 던전으로 복귀"는
  사실상 사망 선고다
- DB가 오래 죽어 있으면 화면이 멈춘 것처럼 보이지만 **손실은 0이다.**
  "이상해 보이는 것"과 "잃는 것" 중 전자를 택한다

> 이 경로만 무한 재시도인 이유: **다른 모든 경로는 실패해도 되돌릴 대상이 있다.**
> 던전 내 조작은 애초에 영속화하지 않고, 사망은 이미 잃는 것이 전제다.
> 탈출만이 "얻은 것을 확정하는" 유일한 지점이다.

## Migration Plan

기존 시스템을 바꾸지 않는다 — 아이템 시스템 자체가 신규다.

1. `GameSession`에 `_handledRequests` + `TryBeginRequest` 추가 → 기존 동작 무변화
2. `GDBQueue` 작업에서 `room->DoAsync(...)` 되튕기는 패턴을 **지급 트랜잭션에 먼저
   적용해 검증**한다 (지금은 편도라 응답만 보낸다) → 배선이 동작함을 확인
3. 아이템 적재를 `Handle_C_ENTER_GAME`의 기존 `characters` 조회에 합류
4. 탈출·사망 커밋 경로 구현

**Rollback plan**: 던전 내 조작에 DB 쓰기를 추가하면 Alternative 1로 이행할 수 있다.
스키마는 그대로 쓸 수 있으므로 되돌리는 비용이 낮다.

## Validation Criteria

- [ ] 던전 내 착용·루팅 100회 동안 `GDBQueue` 작업이 **0건** 추가된다
- [ ] 착용 요청 → 응답 지연이 Room flush P95 예산(16.6 ms) 안에 들어간다
- [ ] 같은 `request_id`로 루팅을 재전송하면 **아이템이 하나만** 들어온다 (AC-IE-49a)
- [ ] 탈출 커밋 실패를 인위적으로 주입하면 플레이어가 **탈출 지점에 무적으로 대기**하고,
      DB 복구 후 **자동으로 커밋되어** 베이스캠프로 전환된다 — 아이템 소실 0
- [ ] 그 대기 중에 몬스터·타 플레이어 공격을 받아도 **사망하지 않는다**
- [ ] 런 도중 서버를 강제 종료하면 재시작 후 플레이어가 **입장 전 인벤**으로 복귀한다
- [ ] 위 시나리오 어디에서도 **아이템이 복제되지 않는다**
