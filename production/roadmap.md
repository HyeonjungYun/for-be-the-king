# For be the King — 개발 로드맵 v2.0

> **v1.0은 다른 게임의 로드맵이었다.** UE Dedicated Server + `UReplicationGraph`, 구역당 12~16인,
> 심리스 월드, 부분사망, 시즌 & 프레스티지 — 전부 폐기되었다.
>
> 특히 **"16인 시뮬 부하에서 서버 프레임 < 16.6 ms"** 게이트가 남아 있어
> *존재하지 않는 시스템에 대한 검증을 통과 기준으로 삼는* 상태였다. **151행 중 약 95행이 무효였다.**
>
> 이 문서는 **자체 IOCP 서버 · 층당 30명 · 1인 개발 · 고정 발표일** 기준으로 다시 썼다.

> ✅ **결정 3건 확정 (2026-08-11)** — §8 참조.
> 장비-스킬 결속(USP)은 **6슬롯 구조**로 P1.5에 배정되었고, **절삭은 하지 않는다.**
> 대신 **데모 준비 기간을 포기**해 14주 전체를 개발에 쓴다.

## 0. 📊 baseline 실측 — **Release** (2026-08-14)

**측정 조건**: 로컬 단일 머신 · `DummyClient -bots N` · 워커 스레드 5 · 10초 창
✅ **빌드 구성: Release** (`/O2`, `/MD`) — P3/P5 판단에 쓸 수 있는 값이다.
✅ **인원 단계마다 서버 재시작** · 히스토그램 **창 단위 리셋** 적용 — 인원별 값이 섞이지 않는다.
각 인원당 5개 창을 측정했고 창 간 p95 편차는 0이었다.

| 인원 | SV-1 p95 | SV-1 p99 | SV-1 max | SV-5 sent | SV-5 per-client | SV-6 메모리 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| **3** ✅ | **≤250 us** | **≤500 us** | 0.64 ms | 0.026 Mbps | 8.8 kbps | 74.7 MB |
| **8** ✅ | ≤2,000 us | ≤2,000 us | 4.2 ms | 0.247 Mbps | 30.9 kbps | 77.8 MB |
| **16** ✅ | ≤8,000 us | ≤8,000 us | 10.2 ms | 1.055 Mbps | 65.9 kbps | 82.8 MB |
| **30** 🔴 | **≤33,000 us FAIL** | ≤33,000 us | 30.5 ms | 3.83 Mbps | 127.6 kbps | 91.6 MB |
| 기준 | < 16,600 | < 33,000 | < 100,000 | ≤ 12 Mbps | ≤ 400 kbps | ≤ 130 MB |

**이동 검증 오탐 0건** — 전 구간 `MOVE REJECT` · `BOT SNAPBACK` 모두 0.

| 게이트 | 판정 |
| ---- | ---- |

### Debug(08-13) → Release(08-14) 비교

| 인원 | Debug p95 | **Release p95** | Debug max | **Release max** |
| ---- | ---- | ---- | ---- | ---- |
| 16 | ≤16,600 us | **≤8,000 us** | 15.1 ms | **10.2 ms** |
| 30 | ≤33,000 FAIL | **≤33,000 FAIL** | 43.6 ms | **30.5 ms** |

30인 p99는 `100,000 FAIL → 33,000 PASS`, max는 `43.6 → 30.5 ms` 로 개선됐다.
**그러나 p95는 여전히 FAIL이다.**

> Debug 표의 p95는 누적 히스토그램 때문에 **실제보다 좋게** 나온 값이었다(앞선 저인원
> 표본에 희석). 그걸 감안하면 Release의 실제 개선폭은 위 표보다 크다 — **그래도 30인은 못 넘는다.**

### 대역폭이 여전히 정확히 O(N²)다

```
3→8    인원 2.67배  →  대역폭 9.4배   (2.67² = 7.1)
8→16   인원 2.00배  →  대역폭 4.27배  (4.0)
16→30  인원 1.88배  →  대역폭 3.63배  (3.5)
```

**원인**: `Room::Broadcast` 가 이동 패킷 1건마다 N−1 회 `Session::Send` 를 호출한다.

flush **빈도**는 N과 무관하게 ~61회/초로 일정한데 **1회 소요 시간**이 N² 로 늘어난다.
단일 `Room` JobQueue 는 직렬 실행이므로 여기가 벽이다.

> 🔴 **결론: 최적화 빌드로 우회되지 않는다. 패킷 병합이 필요하다.**
> 목표 — flush 1회당 `Session::Send` 호출 **551 → 29**.
> `.proto` 변경이 따르므로 🔴 사용자 소유 작업이다.

### ⚠️ 계측 오차 2건 — **둘 다 해소됨 (같은 날)**

**① 봇 송신율이 목표에 못 미쳤다** → `timeBeginPeriod(1)` 로 해결.
`sleep_for(33ms)` 가 기본 타이머 해상도(15.6ms) 단위로 올림돼 실제로는 46.8ms 잤다.
실측 21.98 Hz → 계산값 21.4 Hz 와 일치. 해상도를 1ms 로 올린 뒤 **28.64 Hz (목표의 95%)**.

**② 송신율 카운터 자체가 틀렸다** — `DummyClient.cpp:117` 에서 마이크로초→초 나눗셈이
`/100000.0` 이었다(0 하나 누락). 실제의 1/10 로 찍혔다. `/1000000.0` 으로 수정.

## 0-1. ✅ 패킷 병합 적용 후 (2026-08-14) — **30인 전 게이트 통과**

**변경 요약**: `C_MOVE` 수신 시 즉시 브로드캐스트하던 것을 **33ms(30Hz) 배치**로 전환.
`S_MOVE` 를 `repeated PosInfo infos` + `bool correction` 으로 바꾸고, `Room::FlushMoves` 가
dirty 오브젝트만 모아 **직렬화 1회 · 세션당 Send 1회** 로 보낸다.
스냅백은 `correction = true` 단건이며 수신자는 배치에서 자기 id 항목을 무시한다.

**측정 조건**: Release · 30봇 · 실측 송신율 **28.64 Hz** (목표 30Hz 의 95%)

| 항목 | 병합 전 (22 Hz) | **병합 후 (28.6 Hz)** | 기준 | 판정 |
| ---- | ---- | ---- | ---- | ---- |
| **SV-1 p95** | ≤33,000 us **FAIL** | **≤100 us** | < 16,600 | ✅ **166배 여유** |
| **SV-1 p99** | ≤33,000 us | **≤2,000 us** | < 33,000 | ✅ |
| **SV-1 max** | 30.5 ms | **2.5 ~ 3.2 ms** | < 100,000 | ✅ |
| **SV-5 sent** | 3.83 Mbps | **3.20 Mbps** | ≤ 12 | ✅ |
| **SV-5 per-client** | 127.6 kbps | **107 kbps** | ≤ 400 | ✅ |
| **SV-6 메모리** | 91.6 MB | **91.7 MB** | ≤ 130 | ✅ |
| `[BOT SNAPBACK]` | 0건 | **0건** | 0 | ✅ |

> **부하가 30% 늘어난 상태에서 나온 수치다.** 병합 전 컬럼은 22 Hz, 병합 후는 28.6 Hz 다.

### 아웃바운드가 클라 송신율에서 분리됐다

```
봇 송신율   22 → 28.6 Hz   (+30%)
recv        0.132 → 0.170 Mbps  (+29%)   ← 인바운드는 늘었는데
sent        3.22  → 3.22 Mbps   (  0%)   ← 아웃바운드는 그대로
```

flush 주기가 33ms 고정이라 **한 틱에 클라가 몇 번을 보내든 브로드캐스트는 위치 1개**로 합쳐진다.
서버 업로드 상한이 `flush주기 × 인원` 으로 고정되므로, **악성 클라가 초당 1000번 보내도
아웃바운드는 늘지 않는다.** 병합의 의도치 않은 방어 효과다.

### 무엇이 줄었나 — 대역폭이 아니라 호출 수다

`sent` 는 16% 밖에 안 줄었다. 좌표 데이터는 여전히 N−1 명에게 복사되고,
아낀 것은 **패킷 헤더 28개** 뿐이기 때문이다.

```
30인 30Hz 기준  Session::Send 호출   26,100/초 → 900/초   (29배)
```

**병목은 대역폭이 아니라 락 + `WSASend` 호출 수였다.** p95 가 330배 좋아진 이유가 이것이다.

### 🔴 남은 O(N²) — 동시 입장

첫 창의 `max=47,810us` 는 30봇이 **동시 접속한 순간**이다.
`Room::EnterRoom` 은 입장자마다 `S_SPAWN` 을 O(N) 브로드캐스트하므로 **동시 입장은 여전히 O(N²)** 다.
기준선(100ms) 안이고 입장은 드문 이벤트라 지금 고칠 일은 아니다.
→ **P5 에서 30인 동시 입장을 시험할 때 다시 볼 것.**

> ⚠️ **2026-08-23 정정 — 이 진단은 틀렸다.** 계측해보니 입장 처리는 전체의 10% 미만이었다.
> § 0-3 참조.

## 0-2. ✅ 게이트 G1 — 전투 패킷 대역폭 (2026-08-18)

> 로드맵이 G1 에서 명시적으로 요구한 **"전투 패킷 대역폭 증가분 기록"** 이다.

**측정 조건**: Release · 30봇 · 봇 송신율 **28.46 Hz** · **봇 공격 29.9/초**
봇이 가장 가까운 상대를 추격해 사거리 150cm 안에서 초당 1회 공격한다.
죽으면 접속을 끊고 1초 안에 새 세션으로 복귀한다(리스폰이 없으므로 재접속이 유일한 수단).

| 항목 | 이동만 | **전투 포함** | 증가분 | 기준 | 판정 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| **SV-1 p95** | ≤100 us | **≤100 us** | **0** | < 16,600 | ✅ |
| SV-1 p99 | ≤2,000 us | ≤2,000 us | 0 | < 33,000 | ✅ |
| SV-1 max | 2.5~3.2 ms | 2.2 ms | — | < 100,000 | ✅ |
| **SV-5 sent** | 3.20 Mbps | **3.30 Mbps** | **+3.1%** | ≤ 12 | ✅ |
| SV-5 per-client | 107 kbps | 110 kbps | +2.8% | ≤ 400 | ✅ |
| SV-5 recv | 0.170 Mbps | 0.174 Mbps | +2.4% | — | — |
| **SV-6 메모리** | 91.7 MB | **91.9 MB** | +0.2 MB | ≤ 130 | ✅ |

### 전투 패킷은 이동 대비 무시할 수준이다

```
30봇 × 초당 1회 공격  =  30 공격/초
33ms 배치로 묶으면      →  틱당 약 1건
이동은 틱당 30건        →  전투는 이동의 1/30
```

**배치 구조가 전투에도 그대로 효과를 낸다.** `S_ATTACK` · `S_DAMAGE` 가 각각 초당 30건이지만
33ms 창에 모이면 틱당 1건씩이라 브로드캐스트 횟수가 거의 늘지 않는다.

> **12 Mbps 기준에 3.30 이므로 3.6배 여유가 있다.**
> P1.5(스킬) · P2(아이템 이벤트)를 얹을 공간이 충분하다는 뜻이다.
> 🔴 단 **CC 패킷 부하는 아직 안 쟀다** — P1 에는 CC 공급원이 디버그 커맨드뿐이라
> 봇이 CC 를 쓰지 않는다. **P1.5 에서 다시 잰다.**

### 🔴 이 과정에서 찾은 이동 검증 구멍

봇이 스폰 직후 전력으로 달리자 **전원이 1회씩 `[MOVE REJECT]`** 를 맞았다.

```
budget = 10.9288  =  ceiling(391) × dt(0.0280)      ← 딱 한 틱치. 직전 예산이 0
```

`EnterRoom` 이 `lastMoveUs` 만 세팅하고 **`moveBudget` 을 0 으로 두었다.**
이동 예산 모델은 여유가 쌓여 있어야 지터를 흡수하는데 **입장 순간만 여유가 0** 이라
모델이 작동하지 못하는 구간이었다. 입장 시 예산을 가득 채우도록 수정.

> **실제 플레이어도 같은 판정을 받는다.** 지금까지 안 드러난 이유는 사람이 접속하자마자
> 최대 속도로 달리지 않기 때문이다. **봇이 사람보다 가혹한 조건을 만들어 준 것**이고,
> 그것이 부하 생성기를 두는 이유다.

> 📄 봇 전투 상세: `production/server-tasks/2026-08-18-bot-combat.md`

### 대응 — P5(30인) 목표를 위한 최적화 후보

| 방법 | 효과 | 비용 |
| ---- | ---- | ---- |
| **패킷 병합** — 한 flush 의 move 를 `repeated` 로 묶어 1회 브로드캐스트 | 551회 → **29회** | 🔴 `.proto` 변경 + 양측 핸들러 재생성 |
| **AOI 거리 컬링** | 보이는 대상에게만 | 중간. `networking.md` 에서 "선택"으로 분류됨 |
| flush 배치 상한 | p95 만 개선, 총량 불변 | 낮음 |

**패킷 병합이 압도적이다.** 단 P0 범위가 아니며, **P3(16인) 게이트 전에** 착수하는 것이 맞다 —
16인에서 이미 경계이므로 P3 에서 바로 막힌다.

### 🔴 1차 가설은 틀렸다 — 기록으로 남긴다

§ 0-1 이 *"동시 입장이 O(N²)"* 라고 지목했고 그 전제로 `Room::EnterRoom` 을 배치화했다.
**그리고 계측해보니 주범이 아니었다.**

```
[ENTER] n=30  avg=190us max=4361us     30건 총합 5.7ms
flush max                              60~72ms

→ 입장 처리는 전체의 10% 미만
```

진짜 원인은 **`FlushMoves` 브로드캐스트**였다. 120명이 서로를 전부 보므로 틱당
`119 × 119 ≈ 14,161` 회의 `Send` 가 돈다. § 0-1 이 이미 *"병목은 대역폭이 아니라
락 + WSASend 호출 수"* 라고 적어놨는데, 같은 병목이 규모를 키우자 다시 나타난 것이다.

> **입장 배치화는 유지한다.** 이번 60ms 를 설명하지 못했을 뿐 `O(N²) → O(N)` 은 옳고,
> 120인 측정에서 **`[ENTER] avg` 가 190us → 96us 로 유지**되어 효과가 확인됐다.
> O(N²) 였다면 4배(760us)가 됐어야 한다.

### 🔴 최대 성과는 숫자가 아니라 버그였다

제외 목록이 정당한지 확인하려고 `DBConnectionPool::Connect` 를 읽다가 발견했다.

```cpp
if (connection->Connect(...) == false)
{
    delete connection;                      // ① 해제
    for (DBConnection* c : _connections)    // ② 기존 것도 해제 — 컨테이너에선 안 뺐다
    { c->Close(); delete c; }
```

**use-after-free · 이중 해제 · 거짓 성공이 한꺼번에** 있었다. DB 연결이 한 번도
실패한 적이 없어 드러나지 않았을 뿐, MySQL 이 꺼져 있거나 커넥션 한도를 넘기면

> **`DBConnectionPool` 을 "DB가 필요하니 제외"로 넘겼다면 이 코드를 읽을 이유가 없었다.**
> 제외 목록을 넓히는 것은 숫자를 만드는 일이자 **읽지 않을 코드를 정하는 일**이다.

회귀 테스트를 남겼다 — `연결에_실패하면_false를_주고_풀을_비운다`.

### 🔴 커버리지가 먼저 찾아낸 구조 문제 둘

수치를 보기도 전에 드러난 것들이다.

| | |
|---|---|
| `ServerCore` 의 **Debug 구성이 C++14** 였다 | `Release|x64` 에만 `stdcpp20` 이 있었다. Debug 로 빌드할 일이 없어 몰랐고, `string::data()` 가 `const char*` 를 반환해 컴파일이 깨졌다 |
| 테스트 프로젝트가 **`libmysql.lib` 를 링크하지 않았다** | `ServerCore.lib` 안의 `DBConnection.obj` 가 `mysql_*` 를 미해결로 남긴다. `GameServer` 만 링크하고 있었다 |

### 알려진 한계를 테스트로 고정했다

`PercentileUpperUs` 는 표본이 적으면 p95 를 과소평가한다.

```cpp
const uint64 target = static_cast<uint64>(total * p);   // total=1 → target=0
if (acc >= target)                                       // 0 >= 0 → 빈 버킷의 상한을 반환
```

표본 1건이 4000μs 버킷에 있어도 p95 가 100μs 로 보고된다. 실측은 창당 수만 건이라
영향이 없지만 **기동 직후나 짧은 창에서는 낙관적으로 나온다.**

**지금 고치지 않았다.** 고치면 과거 측정치와 비교 기준이 달라진다. 대신
`표본이_적으면_p95를_과소평가한다` 테스트로 **현재 동작을 고정**해 두었다 —
고칠 때 이 테스트가 의도적으로 실패해 변경 지점을 알려준다.

### 남은 것

- `ThreadManager`(29줄) · `NetAddress.h`(1줄) — 테스트 가능하지만 아직 안 썼다.
  **제외하지 않고 분모에 남긴다.** 빼는 순간 할 일 목록에서도 사라진다
- `ServerStats::Dump`(30줄) — 콘솔 출력. 계산부는 `PercentileUpperUs` 로 분리해 검증 완료
- CI 에서 `--gtest_repeat` 반복 실행 (SV-4 요구사항)

## 0-6. ✅ 지급 트랜잭션 + 멱등성 실측 (2026-09-03)

> 지금까지의 게이트는 전부 **성능**이었다. 이것은 **정확성**이 성능보다 중요한
> 유일한 경로다 — 골드가 두 번 들어가면 빨라도 소용이 없다.

**측정 조건**: **Release 빌드** · 세션 8개 · 유니크 `request_id` 1,000개 ·
각 세션이 전부 전송 → **총 8,000 요청**. 모든 세션이 **같은 캐릭터**를 노린다.

### 설계 — INSERT 가 먼저다

```sql
START TRANSACTION;
  SELECT gold FROM characters WHERE character_id = ? FOR UPDATE;  -- 잠금 순서 고정
  INSERT INTO reward_grants (request_id, ...);                    -- PK 충돌 = 이미 지급됨
  UPDATE characters SET gold = gold + ?;
COMMIT;
```

`request_id` 가 **PRIMARY KEY 인 것이 멱등성의 전부다.** 두 번째 요청은 중복
키(1062)로 튕기고, 그 실패가 곧 "이미 지급됨"을 뜻한다. 별도 조회가 필요 없다.

> **"조회해서 없으면 INSERT" 는 안 된다.** 두 요청이 동시에 오면 둘 다 "없음"을
> 보고 둘 다 지급한다. **유일 인덱스만이 이것을 막는다.**

**`UPDATE` 를 먼저 하면 안 된다.** 중복을 감지하기 전에 골드가 이미 올라간다.

### 결과

| | `FOR UPDATE` 없음 | **`FOR UPDATE` 있음** |
|---|---|---|
| **데드락(1213)** | 수십 건 | **0건** |
| `GRANT_OK` | 1,000 | **1,000** |
| `GRANT_ALREADY` | 6,062 (집계 오류) | **7,000** |
| 응답 합계 | 불일치 | **8,000 = 요청 수** |
| **DB `reward_grants`** | 1,000행 | 1,000행 |
| **DB `gold`** | 100,000 | 100,000 |
| 처리량 | 2,841 req/s | **1,769 req/s** (−38%) |

**8,000개 동시 요청 중 정확히 1,000번만 지급됐고 잔액이 한 골드도 어긋나지 않았다.**

### 🔴 데드락이 나던 상태에서도 결과는 정확했다

`FOR UPDATE` 이전 측정에서 **데드락이 수십 번 발생했는데도 최종 잔액이 정확했다.**
롤백된 요청은 다른 세션의 같은 `request_id` 재시도가 채웠다.

**이것이 트랜잭션의 존재 이유다.** 실패가 없어서 정확한 게 아니라, 실패해도
부분 반영이 남지 않아서 정확하다.

### 🔴 데드락의 원인은 FOREIGN KEY 였다

```
INSERT INTO reward_grants (..., character_id, ...)
    → FK 검사를 위해 characters 행에 공유 잠금(S)

UPDATE characters SET gold = gold + ?
    → 같은 행에 배타 잠금(X) 필요

T1  S 획득 ──→ X 대기 (T2 의 S 때문)
T2  S 획득 ──→ X 대기 (T1 의 S 때문)
```

**S 를 쥔 채 X 로 올리려는 것**이 문제다. `SELECT ... FOR UPDATE` 로 **X 를 먼저
잡아 잠금 순서를 고정**하니 사라졌다.

| 대안 | 얻는 것 | 잃는 것 |
|---|---|---|
| **`FOR UPDATE`** (채택) | 데드락 0 | 같은 대상 지급이 직렬화 |
| FK 제거 | S 잠금 자체가 사라짐 | 없는 캐릭터에 이력이 남을 수 있음 |
| 데드락 재시도 | 처리량 유지 | 재시도 로직 · 최대 횟수 · 백오프 필요 |

### 🔴 "−38%" 는 FOR UPDATE 의 비용이 아니었다 — 정정

`FOR UPDATE` 도입 직후 처리량이 2,841 → 1,769 req/s 로 떨어진 것을 보고
**"데드락을 없앤 대가"** 라고 기록했다. 대상을 흩어 다시 재보니 틀렸다.

**3회씩 반복 측정** (Release · 8세션 · 유니크 1,000 · 총 8,000 요청)

| 조건 | 회차 1 | 회차 2 | 회차 3 | **평균** | 편차 |
|---|---|---|---|---|---|
| **집중** (대상 1개) | 1,766.75 | 1,768.17 | 1,766.58 | **1,767.2** | **±0.05%** |
| **분산** (대상 8개) | 3,173.85 | 3,308.19 | 3,179.25 | **3,220.4** | ±2.1% |

```
FOR UPDATE 없음 · 집중    2,841 req/s
FOR UPDATE 있음 · 집중    1,767 req/s   −38%
FOR UPDATE 있음 · 분산    3,220 req/s   ← 없을 때보다도 13% 빠르다
```

**대상을 흩자 `FOR UPDATE` 를 켠 채로도 끄고 집중했을 때보다 빨라졌다.**
`−38%` 는 `FOR UPDATE` 의 비용이 아니라 **"같은 행에 몰릴 때의 직렬화 비용"** 이며,
대상이 흩어지면 직렬화할 일 자체가 없어 사라진다.

> **비교 조건 하나를 고정한 채 다른 하나만 바꿔서 생긴 오독이다.** `FOR UPDATE`
> 유무만 비교하고 "집중"이라는 조건은 상수로 뒀는데, 그 조건이야말로 비용의 원인이었다.
> § 0-4 에서 *"어느 측정과 비교하는지가 결론을 뒤집는다"* 를 겪고도 같은 종류의
> 실수를 반복했다.

분산 조건에서 골드는 8개 캐릭터에 **12,500씩 정확히 균등 분배**됐다(합계 100,000).

### 처리량은 max 와 달리 안정적이다

```
flush max     ±17%    (§ 0-4)
지급 처리량   ±0.05%  (집중) · ±2.1% (분산)
```

**집중 조건의 편차가 0.05%** 다. 직렬화되면 병목이 하나로 고정되어 오히려 재현성이
높아진다. **지표에 따라 신뢰도가 이만큼 다르므로, 반복 횟수도 지표별로 달라야 한다.**

### 재시도는 거의 공짜다

```
전부 ALREADY 인 경우   3,304 req/s
실제 지급 포함         1,769 req/s
```

중복 요청 처리가 실제 지급보다 **87% 빠르다.** `INSERT` 가 중복 키로 즉시 실패하고
반환하기 때문이다. **요청자가 불안해서 여러 번 보내도 서버 비용이 크게 늘지 않는다** —
멱등성 설계에서 중요한 성질이다.

### 🔴 같은 실수를 두 번 했다 — 실패 분기의 `return` 누락

```cpp
if (conn->Excute(query) == false)
{
    conn->Rollback();
    SendGrantResult(..., GRANT_DB_ERROR, 0);
}                                      // 🔴 return 이 없다
if (conn->GetAffectedRows() == 0)      // 롤백된 상태로 흘러 내려온다
{
    SendGrantResult(..., GRANT_NO_TARGET, 0);   // 같은 요청에 두 번째 응답
}
```

**`DBConnectionPool::Connect`(§ 0-5)와 형태가 같다.** 응답만 보내고 `return` 을
빠뜨렸다. 증상은 `replies 8259 > sent 8000` — **응답이 요청보다 많았다.**

> **합계가 맞지 않는 것이 단서였다.** `993 + 5462 + 902 ≠ 8259`. 개별 수치만 봤다면
> "데드락 때문이겠지"로 넘어갔을 것이다. **총합을 함께 찍어두는 계측이 값을 했다.**

### 계측 코드 자체의 결함

`GRANT_ALREADY` 가 6,062로 나온 것은 지급 로직이 아니라 **리포트의 스냅샷 문제**였다.

```cpp
const uint64 ok = GGrantOk.load();       // t1
const uint64 already = GGrantAlready.load(); // t2
const uint64 replies = GGrantReplies.load(); // t3 — 이미 8000
```

`fetch_add` 하나하나는 원자적이지만 **"여러 카운터를 한 순간에 읽는 것"은 보장되지
않는다.** 대기 루프 종료 후 500ms 를 더 두어 값이 안정된 뒤 읽게 고쳤다.

### 🔴 인증을 의도적으로 넣지 않았다

**아무 세션이나 `C_GRANT_REWARD` 를 보내면 골드가 지급된다.** 실무라면 별도 포트 ·
운영툴 전용 키 · 감사 로그가 필요하다.

넣지 않은 이유는 **이번 목표가 "트랜잭션과 멱등성이 실제로 작동하는가"** 이기
때문이다. 인증을 붙이면 부하 도구도 인증을 통과해야 해서 검증하려는 것과 무관한
작업이 늘어난다. **빠뜨린 것이 아니라 알고 뺐다.**

### 남은 것

- 인증 · 별도 포트 · 감사 로그
- 회수(차감) 경로 — `gold` 가 `BIGINT UNSIGNED` 라 언더플로가 0이 아니라 거대한 수가
  된다. 차감을 넣으려면 `WHERE gold >= ?` 를 반드시 함께 걸어야 한다
- ~~지급 대상이 흩어진 조건에서의 처리량~~ ✅ 위 § 정정 참조 — 3,220 req/s
- ~~반복 측정~~ ✅ 조건당 3회씩 완료
- **대상을 더 흩었을 때의 상한** — 8개까지만 재봤다. 120개로 흩으면 DB 스레드 4개가
  병목이 되는 지점이 나올 것이다. 그 수치가 실사용 상한에 가깝다
- **`FOR UPDATE` 없이 분산** — 미측정. 데드락이 나는지부터 확인해야 조합이 완성된다

## 0-8. ✅ 인증 서버 · 아이템 서버 경로 · 빌드 전수 검사 (2026-09-05~06)

**Phase 항목이 아니다.** 포트폴리오 제출(09-07)을 앞두고 § 13 ④ 의 `웹 서버(예정)` 를
채웠고, 그 과정에서 아이템 핸들러를 처음 실행하고 빌드 경고를 전수 확인했다.

### 인증 서버 — C# ASP.NET Core (net10.0)

```
POST /auth/login  →  PBKDF2-SHA256 검증  →  login_sessions INSERT
C_LOGIN(token)    →  login_sessions SELECT (게임 서버 기존 코드 그대로)
```

**게임 서버 코드가 한 줄도 바뀌지 않았다.** 3개월 전 설계에 적어둔 주장이 실측으로 확인됐다.

| PBKDF2-HMAC-SHA256 | 소요 |
|---|---|
| 100,000회 | 11.0 ms |
| 210,000회 | 24.4 ms |
| **600,000회** | **67.6 ms** ← 채택 (OWASP 2023) |

로그인 종단 응답 **79~87 ms**. PBKDF2 가 67.6 ms 이므로 HTTP · DB 왕복 · 직렬화
전부가 11~19 ms — 시간의 80% 를 느린 것이 목적인 함수가 쓴다.

타이밍 방어 확인: 있는 계정 79.0 ms vs 없는 계정 86.7 ms — 구분 불가.

> 🔴 **첫 측정에서 "없는 계정 1.1 ms" 가 나와 방어 실패로 읽었다.** 레이트 리밋
> (분당 10회) 429 였다. 측정이 틀렸고 코드는 정상이었다. **응답 코드를 함께 찍지
> 않으면 이런 것을 놓친다.**

### 아이템 — 핸들러 첫 실행

### 게이트별 함정

**SV-1 — "서버 프레임"의 정의를 먼저 고정하라.**
`technical-preferences.md`의 "16.6 ms (60 Hz 틱 기준, `DoWorkerJob` 루프)"는 **실제 구조와 다르다.**
`Room::UpdateTick`은 **100 ms(10 Hz)** 타이머로 돌고(`Room.cpp:150`), 현재 내용은 `cout` 하나뿐이다.
`HandleMove`는 틱이 아니라 **패킷 수신마다 `DoAsync`** 로 실행된다. **60 Hz 틱은 존재하지 않는다.**
→ 게이트가 재는 것은 **`Room` JobQueue 1회 Flush 소요시간**으로 고정한다. 이것만이 "한 층의 부하"를
직접 반영하는 관찰 가능한 값이다. **계측 코드가 현재 0줄이다.**

**SV-2 — `game-concept.md`의 "DummyClient 하네스 Tier 2 연기"를 이 로드맵이 뒤집는다.**
하네스가 없으면 **SV-1·2·5·6 네 개를 전부 측정할 수 없다.** "30명에서 성립한다"는 계산 결과일 뿐 실측이 아니다.
완전판은 Tier 2가 맞지만, **접속 유지 + 이동 패킷만 흘리는 최소판(약 1일)** 은 MVP로 당긴다.

**SV-3 — 소프트 CC가 들어오는 순간 공식이 깨진다.**
`effective_move_speed(player) × 1.15`는 **장비 보너스만** 반영한다. 공식 1에 **감속 항이 없다** —
소프트 CC는 별도 공식(`slow_effect`)이라 서버가 그것까지 합쳐 "현재 실효 이동속도"를 알아야 한다.
모르면 감속 걸린 플레이어가 정상 이동해도 통과하는 구멍이 생기고, 상한을 올리면 검증이 무의미해진다.
→ **P1 게이트에서 SV-3를 재설계·재검증한다. P0 통과는 P1 통과를 의미하지 않는다.**

**SV-4 — 단위 테스트는 데이터 레이스를 잡지 못한다.**
2026-08-10에 `Session::_sendQueue`에서 실제로 겪었다. `LockQueue::PopAll` 재귀 락은 단일 스레드로도
잡혔지만, `_sendQueue` 레이스는 **다중 스레드 동시 접근 없이는 재현되지 않았다.**
대상: `Session::_sendQueue` · `LockQueue` · `Room::_objects` · `JobQueue` · `GlobalQueue`.
비결정적이므로 **반복 실행이 통과 조건의 일부다.**
⚠️ `ServerCoreTests`에 **ServerCore 프로젝트 참조를 반드시 설정** — 구버전 lib 링크 사고 재발 방지.

**SV-5 — 현재 추정치는 위치 패킷만 센 것이다.**
30 Hz·30명 기준 278 kbps에는 **몬스터 위치 · 전투 패킷 · 아이템 이벤트가 전부 빠져 있다.**
P0 baseline은 하한선이며, 매 게이트마다 **증가분을 기록**한다. 증가율이 선형을 넘으면 그 시점에
AOI를 Tier 2에서 당긴다.

**SV-6 — MVP는 30명까지만 실측 가능하다.**
1층뿐이므로 120 동접 실검증은 Tier 3다. MVP가 주장할 수 있는 것은 **"30명 실측 + 4배 외삽"** 까지다.
문서에 "512 MB 검증 완료"라고 쓰지 말 것. 초과 시 최저비용 레버는 **`RecvBuffer::BUFFER_COUNT` 축소**
(이동 패킷 40바이트에 세션당 640 KB는 과하다).

### 🔴 이 배치의 성격 — "발표를 위해 자르지 않는다"

**절삭은 하지 않는다.** 집 3개 · 몬스터 AI 완전판 · 아이템 등급 표시 · 전투 3주 전부 원안 유지.


> **발표 완성도보다 실제 개발 진도를 택했다.** 발표에서는 "여기까지 됐다"를 정직하게 보여준다.

## 8. ✅ 확정된 결정 (2026-08-11)

### 결정 0 — 아키텍처: **GAS 미채택 · UE 리플리케이션 미사용** ✅

**선택**: `ADR-0001`(Iris vs ReplicationGraph)·`ADR-0002`(GAS 채택) **둘 다 Rejected.**
전투·스킬은 **서버 C++ 권위 + 서버·클라 공유 스킬 데이터 테이블**로 구현한다.
클라는 결과를 받아 **연출만 재생**한다. `GameplayTags` 모듈만 단독 사용 허용.

**근거**: GAS의 절반이 UE 리플리케이션(ASC ReplicationMode · PredictionKey · AttributeSet RepNotify)인데
이 프로젝트에 UE 서버가 없다. 채택하면 **같은 스킬을 서버 C++와 클라 GAS로 두 번, 다른 패러다임으로**
쓰게 되고 — 서버는 사용자 소유, 클라는 에이전트 소유라 **두 구현의 저자까지 갈린다.**

**이득**: 학습 **1~2주 절약** (가용 12주 중) · 이중 구현 위험 소거
**되살아나는 조건**: 스킬 30개 이상 · 또는 UE Dedicated Server로 전환(= 프로젝트 정체성 변경)

> 정식 대체 ADR(**ADR-0003**)은 전투 시스템 GDD와 함께 쓴다. 지금은 앵커가 될 GDD가 없다.
> 🔴 **`ue-gas-specialist` · `ue-replication-specialist` 호출 금지** — `technical-preferences.md`에 명시함.

### 결정 1 — 장비-스킬 결속(USP): **6슬롯 구조** ✅

**선택**: 결속 시스템을 **6슬롯 구조로** 만들고, 스킬 콘텐츠는 **2~3종만** 채운다. 빈 슬롯은 P7에서.

**근거**: 결속 시스템 자체는 슬롯 개수와 무관하다. 비싼 것은 스킬 6종을 각각 설계·구현·밸런싱하는 쪽이다.
구조가 6슬롯이면 **"이 무기를 끼면 Q가 A스킬, 저 무기를 끼면 Q가 B스킬"** 시연이 완전히 성립한다.

**비용**: +1주 (P1.5 신설)

> **왜 뺄 수 없었나**: 스킬을 빼면 **CC 체계 전체가 MVP에서 사라진다.**
> 하드 CC가 무기 스킬이고 소프트 CC가 다른 부위 스킬이기 때문이다. 연쇄로
> **AC-5 · AC-6 · P1 필러 검증 · 대시(공식 3·7b)** 가 전부 검증 불가가 되고,
> 발표 데모가 "우클릭 평타만 있는 탑다운 게임"이 된다.

### 결정 2 — 부족한 시간: **절삭하지 않고 데모 준비를 포기** ✅

**선택**: 아무것도 자르지 않는다. 대신 데모 준비 2.6주 → **4일**.

| 자르지 않은 것 | 원안 유지 |
|---|---|
| 레벨 — 집 3개 | 2주 → **3주로 오히려 늘어남** (P3에 몬스터 AI 포함) |
| 몬스터 AI | 완전판 (추격 + 공격 + 집 보스) |
| 아이템 등급 표시 | 형태 이중부호화 유지 — **색맹 접근성 보존** |
| 전투 | 3주 유지 |
| 통합·검증 | **2주 유지 — 축소 금지 지켜짐** |

**보험**: **11-16에 시연 녹화본 확보** (30분). 당일 크래시 대비.

### 결정 3 — 설계 문서: **정식 GDD 6개 + quick-spec 10개** ✅

| 정식 8섹션 (6개) | quick-spec 1페이지 (10개) |
|---|---|
| 입력 · **이동&카메라 ✅** · 전투 · 아이템&장비 · 인벤토리&사망 · 탈출&타이머 | 네트워킹 · 계정&로그인 · 세이브&영속성 · 스킬 · 장비-스킬결속 · 몬스터AI · 레벨&맵 · 레이더 · HUD · 베이스캠프 |

**기준**: **공식과 수치가 있는 시스템만 정식으로 쓴다.**
데미지 공식 · 저항력 부여량 · 이동속도 클램프 · 드랍 확률 · 게이지 속도는 나중에 밸런싱할 때
"이 숫자가 왜 이건지" 근거가 필요하다. 레이더 감지 대상 목록이나 HUD 표시 항목은 1페이지로 충분하다.

**배정**: 각 Phase 착수 전 **0.5일**을 그 Phase 시스템 문서에 쓴다 (Phase 시간 안에 포함, 별도 시간 불필요).

> **전부 quick-spec으로 가지 않은 이유**: 전투 공식을 코드에만 두면 3개월 뒤 밸런싱할 때
> `K_mitigation = 100`이 왜 100인지 아무도 모른다. 아카이브 combat GDD가 그 근거를 갖고 있어서
> 지금 계승 판단이 가능했던 것과 **정반대 상황**이 된다.
