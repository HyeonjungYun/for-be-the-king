# For be the King — 개발 로드맵 v2.0

> **v1.0은 다른 게임의 로드맵이었다.** UE Dedicated Server + `UReplicationGraph`, 구역당 12~16인,
> 심리스 월드, 부분사망, 시즌 & 프레스티지 — 전부 폐기되었다.
>
> 특히 **"16인 시뮬 부하에서 서버 프레임 < 16.6 ms"** 게이트가 남아 있어
> *존재하지 않는 시스템에 대한 검증을 통과 기준으로 삼는* 상태였다. **151행 중 약 95행이 무효였다.**
>
> 이 문서는 **자체 IOCP 서버 · 층당 30명 · 1인 개발 · 고정 발표일** 기준으로 다시 썼다.

> ✅ **결정 3건 확정 (2026-08-11)** — §8 참조.
> 장비-스킬 결속(USP)은 **6슬롯 구조**로 P1.5에 배정되었고, **절삭은 하지 않는다.**
> 대신 **데모 준비 기간을 포기**해 14주 전체를 개발에 쓴다.

## 0. 📊 baseline 실측 (2026-08-13)

**측정 조건**: 로컬 단일 머신 · `DummyClient -bots N` · 워커 스레드 5 · 10초 창
🔴 **빌드 구성: Debug** — 최적화가 꺼져 있어 실제보다 **2~10배 느리다.**
**아래 숫자는 상한선으로만 쓸 것.** Release 재측정 전까지 P3/P5 판단 근거로 삼지 말 것.

| 인원 | SV-1 p95 | SV-1 p99 | SV-1 max | SV-5 sent | SV-5 per-client | SV-6 메모리 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| **3** ✅ | **≤250 us** | **≤500 us** | 5.5 ms | 0.027 Mbps | 8.8 kbps | 77.0 MB |
| **8** ✅ | ≤2,000 us | ≤4,000 us | 5.5 ms | 0.190 Mbps | 23.7 kbps | 80.2 MB |
| **16** ⚠️ | ≤16,600 us | ≤16,600 us | 15.1 ms | 0.667 Mbps | 41.7 kbps | 85.8 MB |
| **30** 🔴 | **≤33,000 us FAIL** | **≤100,000 us FAIL** | 43.6 ms | 2.424 Mbps | 80.8 kbps | 94.4 MB |
| 기준 | < 16,600 | < 33,000 | < 100,000 | ≤ 12 Mbps | ≤ 400 kbps | ≤ 130 MB |

**✅ P0 게이트(3인) 통과.** 여유 66배.

### 대역폭이 정확히 O(N²)다

```
3→8    인원 2.67배  →  대역폭 7.0배   (2.67² = 7.1)
8→16   인원 2.00배  →  대역폭 3.5배   (4.0)
16→30  인원 1.88배  →  대역폭 3.6배   (3.5)
```

**원인**: `Room::Broadcast` 가 이동 패킷 1건마다 N−1 회 `Session::Send` 를 호출한다.
30명이면 한 flush(평균 19 job)에 **551회 WSASend** → 60us × 551 ≈ 33 ms.

**무너지는 지점은 16명과 30명 사이다.** 16인에서 이미 p95가 기준선에 딱 붙었다.

### 🔴 이 숫자를 최종으로 쓰면 안 되는 이유 2개

**① 히스토그램이 누적이라 인원별 값이 섞였다.**
`_flushBuckets` 를 덤프 시 리셋하지 않는다. 30인 창의 p95 는 앞선 3·8·16인 표본
1,973개에 희석돼 있다(30인 구간의 실제 표본은 466개). **진짜 30인 p95 는 표보다 나쁘다.**
→ 다음 측정 시 **인원 단계마다 서버를 재시작**하거나 히스토그램을 구간값으로 바꿀 것.

**② 봇이 30Hz 로 못 보내고 있다.**

| | |
| ---- | ---- |
| 문서 예측 (30명) | per-client **278 kbps** |
| 실측 | per-client **80.8 kbps** — 3.4배 낮음 |
| 역산 송신율 | `0.088 Mbps ÷ 30봇 ÷ 40B` ≈ **11 Hz** |

`this_thread::sleep_for(33ms)` 가 Windows 스케줄러 해상도(~15.6ms)에 걸려 실제로는
46ms 이상 자고, `TickBots` 의 30봇 순회 시간이 더해진다.
**즉 현재 측정은 실제 부하의 약 1/3이다.** 진짜 30Hz 면 `sent ≈ 7.3 Mbps`,
flush 는 3배 더 나쁘다.
→ 봇에 실제 송신율 카운터를 넣고 `timeBeginPeriod(1)` 또는 스핀 대기로 보정할 것.

### 대응 — P5(30인) 목표를 위한 최적화 후보

| 방법 | 효과 | 비용 |
| ---- | ---- | ---- |
| **패킷 병합** — 한 flush 의 move 를 `repeated` 로 묶어 1회 브로드캐스트 | 551회 → **29회** | 🔴 `.proto` 변경 + 양측 핸들러 재생성 |
| **AOI 거리 컬링** | 보이는 대상에게만 | 중간. `networking.md` 에서 "선택"으로 분류됨 |
| flush 배치 상한 | p95 만 개선, 총량 불변 | 낮음 |

**패킷 병합이 압도적이다.** 단 P0 범위가 아니며, **P3(16인) 게이트 전에** 착수하는 것이 맞다 —
16인에서 이미 경계이므로 P3 에서 바로 막힌다.

v1.0의 실패는 게이트를 Phase 0에 한 번 놓고 끝낸 것이었다. **부하는 기능이 쌓일수록 커진다** —
대역폭과 프레임은 P0가 아니라 **P5에서 최악**이 된다.

### 게이트별 함정

**SV-1 — "서버 프레임"의 정의를 먼저 고정하라.**
`technical-preferences.md`의 "16.6 ms (60 Hz 틱 기준, `DoWorkerJob` 루프)"는 **실제 구조와 다르다.**
`Room::UpdateTick`은 **100 ms(10 Hz)** 타이머로 돌고(`Room.cpp:150`), 현재 내용은 `cout` 하나뿐이다.
`HandleMove`는 틱이 아니라 **패킷 수신마다 `DoAsync`** 로 실행된다. **60 Hz 틱은 존재하지 않는다.**
→ 게이트가 재는 것은 **`Room` JobQueue 1회 Flush 소요시간**으로 고정한다. 이것만이 "한 층의 부하"를
직접 반영하는 관찰 가능한 값이다. **계측 코드가 현재 0줄이다.**

**SV-2 — `game-concept.md`의 "DummyClient 하네스 Tier 2 연기"를 이 로드맵이 뒤집는다.**
하네스가 없으면 **SV-1·2·5·6 네 개를 전부 측정할 수 없다.** "30명에서 성립한다"는 계산 결과일 뿐 실측이 아니다.
완전판은 Tier 2가 맞지만, **접속 유지 + 이동 패킷만 흘리는 최소판(약 1일)** 은 MVP로 당긴다.

**SV-3 — 소프트 CC가 들어오는 순간 공식이 깨진다.**
`effective_move_speed(player) × 1.15`는 **장비 보너스만** 반영한다. 공식 1에 **감속 항이 없다** —
소프트 CC는 별도 공식(`slow_effect`)이라 서버가 그것까지 합쳐 "현재 실효 이동속도"를 알아야 한다.
모르면 감속 걸린 플레이어가 정상 이동해도 통과하는 구멍이 생기고, 상한을 올리면 검증이 무의미해진다.
→ **P1 게이트에서 SV-3를 재설계·재검증한다. P0 통과는 P1 통과를 의미하지 않는다.**

**SV-4 — 단위 테스트는 데이터 레이스를 잡지 못한다.**
2026-08-10에 `Session::_sendQueue`에서 실제로 겪었다. `LockQueue::PopAll` 재귀 락은 단일 스레드로도
잡혔지만, `_sendQueue` 레이스는 **다중 스레드 동시 접근 없이는 재현되지 않았다.**
대상: `Session::_sendQueue` · `LockQueue` · `Room::_objects` · `JobQueue` · `GlobalQueue`.
비결정적이므로 **반복 실행이 통과 조건의 일부다.**
⚠️ `ServerCoreTests`에 **ServerCore 프로젝트 참조를 반드시 설정** — 구버전 lib 링크 사고 재발 방지.

**SV-5 — 현재 추정치는 위치 패킷만 센 것이다.**
30 Hz·30명 기준 278 kbps에는 **몬스터 위치 · 전투 패킷 · 아이템 이벤트가 전부 빠져 있다.**
P0 baseline은 하한선이며, 매 게이트마다 **증가분을 기록**한다. 증가율이 선형을 넘으면 그 시점에
AOI를 Tier 2에서 당긴다.

**SV-6 — MVP는 30명까지만 실측 가능하다.**
1층뿐이므로 120 동접 실검증은 Tier 3다. MVP가 주장할 수 있는 것은 **"30명 실측 + 4배 외삽"** 까지다.
문서에 "512 MB 검증 완료"라고 쓰지 말 것. 초과 시 최저비용 레버는 **`RecvBuffer::BUFFER_COUNT` 축소**
(이동 패킷 40바이트에 세션당 640 KB는 과하다).

### 🔴 이 배치의 성격 — "발표를 위해 자르지 않는다"

**절삭은 하지 않는다.** 집 3개 · 몬스터 AI 완전판 · 아이템 등급 표시 · 전투 3주 전부 원안 유지.
대신 **데모 준비 2.6주를 포기**하고 그 시간을 개발에 쓴다.

```
전체        08-11 → 11-21  =  102일 = 14.6주
개발 배정                     98일 = 14.0주   (P0 +1주, P1.5 +1주 포함)
발표 준비                      4일
```

**대가 — 발표 당일 크래시가 나면 대안이 없다.** 리허설 3회도 없다.
유일한 보험이 **11-16 녹화본**이다. 30분 투자로 "서버가 안 뜨거나 크래시가 나도 발표는 성립한다"를 산다.

> 이것은 **의식적 선택**이다. 11/21은 성과 시연일이지 종료일이 아니므로,
> **발표 완성도보다 실제 개발 진도를 택했다.** 발표에서는 "여기까지 됐다"를 정직하게 보여준다.

## 8. ✅ 확정된 결정 (2026-08-11)

### 결정 0 — 아키텍처: **GAS 미채택 · UE 리플리케이션 미사용** ✅

**선택**: `ADR-0001`(Iris vs ReplicationGraph)·`ADR-0002`(GAS 채택) **둘 다 Rejected.**
전투·스킬은 **서버 C++ 권위 + 서버·클라 공유 스킬 데이터 테이블**로 구현한다.
클라는 결과를 받아 **연출만 재생**한다. `GameplayTags` 모듈만 단독 사용 허용.

**근거**: GAS의 절반이 UE 리플리케이션(ASC ReplicationMode · PredictionKey · AttributeSet RepNotify)인데
이 프로젝트에 UE 서버가 없다. 채택하면 **같은 스킬을 서버 C++와 클라 GAS로 두 번, 다른 패러다임으로**
쓰게 되고 — 서버는 사용자 소유, 클라는 에이전트 소유라 **두 구현의 저자까지 갈린다.**

**이득**: 학습 **1~2주 절약** (가용 12주 중) · 이중 구현 위험 소거
**되살아나는 조건**: 스킬 30개 이상 · 또는 UE Dedicated Server로 전환(= 프로젝트 정체성 변경)

> 정식 대체 ADR(**ADR-0003**)은 전투 시스템 GDD와 함께 쓴다. 지금은 앵커가 될 GDD가 없다.
> 🔴 **`ue-gas-specialist` · `ue-replication-specialist` 호출 금지** — `technical-preferences.md`에 명시함.

### 결정 1 — 장비-스킬 결속(USP): **6슬롯 구조** ✅

**선택**: 결속 시스템을 **6슬롯 구조로** 만들고, 스킬 콘텐츠는 **2~3종만** 채운다. 빈 슬롯은 P7에서.

**근거**: 결속 시스템 자체는 슬롯 개수와 무관하다. 비싼 것은 스킬 6종을 각각 설계·구현·밸런싱하는 쪽이다.
구조가 6슬롯이면 **"이 무기를 끼면 Q가 A스킬, 저 무기를 끼면 Q가 B스킬"** 시연이 완전히 성립한다.

**비용**: +1주 (P1.5 신설)

> **왜 뺄 수 없었나**: 스킬을 빼면 **CC 체계 전체가 MVP에서 사라진다.**
> 하드 CC가 무기 스킬이고 소프트 CC가 다른 부위 스킬이기 때문이다. 연쇄로
> **AC-5 · AC-6 · P1 필러 검증 · 대시(공식 3·7b)** 가 전부 검증 불가가 되고,
> 발표 데모가 "우클릭 평타만 있는 탑다운 게임"이 된다.

### 결정 2 — 부족한 시간: **절삭하지 않고 데모 준비를 포기** ✅

**선택**: 아무것도 자르지 않는다. 대신 데모 준비 2.6주 → **4일**.

| 자르지 않은 것 | 원안 유지 |
|---|---|
| 레벨 — 집 3개 | 2주 → **3주로 오히려 늘어남** (P3에 몬스터 AI 포함) |
| 몬스터 AI | 완전판 (추격 + 공격 + 집 보스) |
| 아이템 등급 표시 | 형태 이중부호화 유지 — **색맹 접근성 보존** |
| 전투 | 3주 유지 |
| 통합·검증 | **2주 유지 — 축소 금지 지켜짐** |

**보험**: **11-16에 시연 녹화본 확보** (30분). 당일 크래시 대비.

### 결정 3 — 설계 문서: **정식 GDD 6개 + quick-spec 10개** ✅

| 정식 8섹션 (6개) | quick-spec 1페이지 (10개) |
|---|---|
| 입력 · **이동&카메라 ✅** · 전투 · 아이템&장비 · 인벤토리&사망 · 탈출&타이머 | 네트워킹 · 계정&로그인 · 세이브&영속성 · 스킬 · 장비-스킬결속 · 몬스터AI · 레벨&맵 · 레이더 · HUD · 베이스캠프 |

**기준**: **공식과 수치가 있는 시스템만 정식으로 쓴다.**
데미지 공식 · 저항력 부여량 · 이동속도 클램프 · 드랍 확률 · 게이지 속도는 나중에 밸런싱할 때
"이 숫자가 왜 이건지" 근거가 필요하다. 레이더 감지 대상 목록이나 HUD 표시 항목은 1페이지로 충분하다.

**배정**: 각 Phase 착수 전 **0.5일**을 그 Phase 시스템 문서에 쓴다 (Phase 시간 안에 포함, 별도 시간 불필요).

> **전부 quick-spec으로 가지 않은 이유**: 전투 공식을 코드에만 두면 3개월 뒤 밸런싱할 때
> `K_mitigation = 100`이 왜 100인지 아무도 모른다. 아카이브 combat GDD가 그 근거를 갖고 있어서
> 지금 계승 판단이 가능했던 것과 **정반대 상황**이 된다.
