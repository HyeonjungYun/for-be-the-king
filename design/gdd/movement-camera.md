## Overview

이동 & 카메라 시스템은 입력 시스템이 제공하는 `IA_Move` raw 벡터와 커서 월드좌표를 받아, **WASD 8방향 이동**과 **커서를 향한 조준(facing)** 으로 변환하고, 플레이어를 따라가는 **완전 고정 탑다운 카메라**를 구동하는 Core 계층이다. UE 5.8 `CharacterMovementComponent`(CMC) 위에 구현되며, 클릭이동이 아니라 **이동 방향과 바라보는 방향을 분리**한다 — WASD로 빠지면서 커서로 겨냥하는 LoL식 조작(strafe·kiting)이 이 게임 조작 정체성의 출발점이다. 이동은 **클라이언트가 즉시 예측해 그리고 자체 IOCP 서버가 속도 상한으로 검증**하는 구조를 따르며, UE 리플리케이션과 CMC 내장 네트워크 예측(`SavedMove`)은 사용하지 않는다.

**카메라는 이 게임에서 프레이밍 장치가 아니라 P4의 실행 장치다.** 미니맵이 없으므로 플레이어가 얻는 공간 정보는 **화면에 보이는 것 + 근거리 레이더**뿐이고, 화면에 무엇이 얼마나 보이는지를 정하는 것이 곧 카메라 파라미터다. 회전·줌 조작을 일절 주지 않는 이유도 여기 있다 — **줌아웃으로 시야를 넓힐 수 있으면 "정보가 가장 비싼 자원"이 성립하지 않는다.** 이 시스템이 없으면 추격·회피·매복·조준 같은 어떤 공간적 플레이도 성립하지 않는다.

## Player Fantasy

### 이동 — **"몸은 도망치고, 손은 겨눈다"**

이동의 판타지는 **분리의 쾌감**이다. 다리는 WASD로 안전하게 빠지면서, 눈과 커서는 적을 놓지 않는 **카이팅**. 초보는 이동과 조준이 뒤엉켜 한쪽을 놓치지만, 숙련자는 둘을 독립적으로 부려 "쫓기면서 역으로 꽂는" 순간을 만든다.

**그리고 이 게임에서 그 숙련은 취미가 아니다.** P2("힘은 손에 든 것에서만 나온다")가 캐릭터 성장을 금지했으므로, 100시간을 해도 스탯은 처음과 같다. **달라지는 것은 손에 든 장비와, 그 손을 쓰는 실력뿐이다.** 카이팅을 몸에 익히는 것은 이 게임에서 강해지는 거의 유일한 경로이고, 그래서 이 조작의 손맛은 다른 게임보다 더 무겁게 설계되어야 한다. 어설픈 조작은 "불편함"이 아니라 **성장 경로의 차단**이 된다.

### 카메라 — **"의식되지 않는 것이 성공이다"**

카메라는 정반대의 판타지다. 좋은 탑다운 카메라는 플레이어가 "카메라를 조작한다"고 느끼게 하지 않고, 언제나 필요한 만큼의 시야를 정확한 각도로 프레이밍해 준다. 플레이어가 카메라와 *싸우는* 순간 — 가려짐·못 따라옴·멀미 — 이 곧 실패다.

**다만 이 게임의 카메라에는 두 번째 역할이 있다.** 미니맵이 없고 레이더는 근거리뿐이므로, **화면 밖은 말 그대로 모르는 세계다.** 플레이어는 "지금 내가 보고 있는 것이 내가 아는 전부"라는 감각 위에서 판단해야 한다. 좁은 시야는 불편이 아니라 **긴장의 원천**이다 — 모퉁이 너머에 무엇이 있는지 모른 채로 들어가는 것이 이 게임의 기본 상태다.

**레퍼런스**: League of Legends · Battlerite — 이동으로 빠지며 커서로 스킬샷을 꽂는 손맛. 이동과 조준의 분리가 실력이 되는 구조.
**안티 레퍼런스**: 이동이 커서 방향에 강제로 묶여 도망치며 뒤를 못 보는 조작 · 캐릭터가 벽·적에 걸려 멈칫하는 뭉개짐 · 플레이어를 놓치거나 흔들려 멀미를 유발하는 카메라 · **줌아웃으로 정보를 살 수 있는 카메라**.

## Detailed Design

### Core Rules

**1. 이동 입력 해석** — `IA_Move`(Axis2D raw)를 **월드 기준** 방향으로 해석한다. 카메라가 완전 고정이므로 화면-상단 = 월드-전방이 항상 성립한다. 대각선은 정규화(공식 5). `AddMovementInput`으로 CMC에 전달. *입력=raw, 이동=정규화·가속.*

**2. 속도** — 기본 이동속도는 CMC `MaxWalkSpeed` = **340 cm/s** (노브 `base_move_speed`). 라이즈 기준값이며 층 크기·세션 시간 예산이 전부 이 값에서 파생된다(`game-concept.md` § 공간). **strafe 속도 페널티 없음** — 전 방향 균일. 가감속은 CMC 지상 마찰.

**3. 페이싱 — 항상 커서** — 캐릭터 yaw는 매 틱 **커서 월드좌표**를 향해 회전(공식 2). `bOrientRotationToMovement = false` · `bUseControllerRotationYaw = false`로 두고 **수동 회전**한다. → 이동방향과 무관한 **strafe 운동**이 성립한다.

> 🔴 현재 코드는 `bOrientRotationToMovement = true` (`S1Player.cpp:28`) — **정반대. 수정 대상.**

**4. 로코모션 블렌드** — 애니메이션은 "페이싱 기준 속도 벡터"(전/후/좌우)를 8방향 strafe 블렌드스페이스에 매핑한다. 도망치며 뒤로 겨냥 = 후방 strafe 애님. **문워크 금지.**

**5. 지상 전용 · 기본 회피 없음** — **점프 없음**(2026-08-11 MVP 결정). 보편 이동은 걷기만이며, 대시·블링크·구르기는 **장비에 붙은 스킬**에서 온다(P2). 이동 시스템은 스킬이 호출할 **위치이동 API**(`RequestDash(dir, dist, speed)`)만 제공한다.

**6. 콜리전** — CMC 캡슐. 지오메트리(벽)에 막히고 관통하지 않는다. **폰 간 상호 블로킹**(노브 `pawn_collision`) — 적/타 플레이어를 밀거나 통과하지 못한다.

**7. CC 반응** — 전투 시스템이 `can_move` / `can_turn` 플래그를 공급하면 이동은 **읽고 반응만** 한다. **Root** = 이동 입력 무시(속도 0), 페이싱은 유지. **Stun** = 이동·페이싱 모두 정지. **CC 상태의 권위와 CC 저항력 계산은 전투 시스템 소유** — 이동은 결과 플래그만 본다.

### 8. 카메라 — 완전 고정 (확정값, 2026-08-11)

| 파라미터 | 값 | 근거 |
|---|---|---|
| `TargetArmLength` | **2,600** | 화면 가로 30m 역산 |
| `FieldOfView` | **60°** | 좁은 FOV = 납작한 원근 (아트바이블 ①) |
| pitch | **−60°** (월드 절대) | 아트바이블 확정 |
| `bUsePawnControlRotation` | **false** | 🔴 현재 `true` — 수정 대상 |
| `SetUsingAbsoluteRotation` | **true** | 폰 회전과 완전 분리 |
| `bInheritPitch` / `bInheritYaw` / `bInheritRoll` | **전부 false** | 폰이 돌아도 카메라는 안 돎 |
| **`bDoCollisionTest`** | **false** | 🔴 **UE 기본값이 `true`.** 켜두면 건물·벽에 카메라가 당겨져 시야가 요동친다 |

```
결과:  화면 30m × 19.5m  ·  가시 면적 ≈ 585 m²
      카메라 높이 22.5m · 뒤로 13m
      동시 가시 인원 = 585 ÷ 2,613 = 0.22명 (개활지 균등 분포)
```

**회전·줌 조작을 제공하지 않는다.** 줌아웃으로 시야를 넓힐 수 있으면 P4("정보가 가장 비싼 자원")가 무너진다. 카메라는 lag(공식 4)만 가지며 플레이어 입력을 받지 않는다.

**9. 클라이언트 예측** — 로컬 플레이어는 입력 즉시 CMC로 이동한다. **서버 응답을 기다리지 않는다.** 화면에 보이는 내 캐릭터는 항상 내 입력에 즉각 반응한다.

**10. 서버 검증** 🔴 **서버 영역 — 스펙만 기술** — 클라는 **30Hz**(`MOVE_PACKET_SEND_DELAY = 1/30`)로 위치를 전송하고, 서버는 각 패킷에 대해 다음을 검사한다.

```
Δ거리 ÷ Δ시간  ≤  340 cm/s × 1.15      (15% 여유 = 지연 변동 흡수)

통과 → 브로드캐스트
실패 → 거부 + 마지막 유효 위치로 스냅백
```

구현 위치: `Server/GameServer/ServerPacketHandler.cpp:83` TODO + `Room::HandleMove`. **현재 검증 0줄.**

**11. 원격 프록시 = 시뮬레이션 금지, 재생만** — 타 플레이어는 `MOVE_None` + `SetActorLocation(bSweep = false)`로 서버 좌표를 재생한다. **`bSweep = false`가 핵심** — true면 프록시가 자체 충돌 판정을 다시 해 클라마다 결과가 갈린다. "벽에 막힌 판정"은 조작 주인의 클라에서 이미 끝났다.

`MOVE_None`이라 CMC가 `Velocity`·`Acceleration`을 갱신하지 않으므로, 애니메이션 구동을 위해 **둘 다 수동 주입**한다(공식 6).

### States and Transitions

| State | Entry | Exit | Behavior |
|---|---|---|---|
| `Idle` | 지상 · `IA_Move`=0 | `IA_Move`≠0 / CC | 정지, **커서 페이싱 지속** |

### 1. `effective_move_speed` — 최종 이동속도 ⭐ 크로스시스템

장비 이동속도 보너스는 **가산 스택 후 최종 1회 곱 + 하드캡**. 곱연산(`×(1+x)` 순차)은 아이템 5개 각 +20%에서 `1.2^5 ≈ 2.49배`로 지수 폭주해 PvP 무한 카이팅을 유발하므로 배제한다.

`effective_move_speed = clamp((base_move_speed + flat_ms_bonus) × (1 + Σ percent_ms_bonus_i), ms_min_ratio × base, ms_max_ratio × base)`

| 변수 | 타입 | 범위 | 설명 |
|---|---|---|---|
| `base_move_speed` | float | const **340** cm/s | CMC `MaxWalkSpeed` |
| `flat_ms_bonus` | float | **0–85** cm/s | 장비 고정치 합 — **변경: 150 → 85** |
| `percent_ms_bonus_i` | float | 0.00–0.15 (아이템당) | 가산 스택 — 유지 |
| `ms_min_ratio` | float | const **0.5** | 하한 비율 — 유지 |
| `ms_max_ratio` | float | const **1.5** | 상한 비율 — 유지 |

**출력 범위:** 하드 클램프 **[170, 510] cm/s**
**예시:** base=340, flat=85(캡), Σpercent=0.45 → `(340+85)×1.45 = 616.25` → 클램프 → **510 cm/s**
일반 로드아웃: flat=40, Σpercent=0.10 → `(340+40)×1.10 = 418 cm/s` (캡 미발동)

**근거:** `flat_ms_bonus` 150은 base 600에서 **25%** 였다. 340에 그대로 두면 **44%** 가 되어 아이템 하나로 캡 근처까지 밀린다. `150 × (340/600) = 85` → 25% 비율이 정확히 보존된다. 비율 상수들은 이미 base 상대값이라 손대지 않는다. 상한 510은 대시 최소값(450)과 비슷하고 최대값(1360)보다 훨씬 낮아 **"이속 아이템으로 대시를 흉내낸다"는 밸런스 침식이 없다.**

### 2. `cursor_facing_yaw` — 커서 페이싱 보간

`target_yaw = atan2(cursor.Y − actor.Y, cursor.X − actor.X)`
`new_yaw = actor_yaw + wrap180(target_yaw − actor_yaw) × clamp(dt × face_interp_speed, 0, 1)`

| 변수 | 타입 | 범위 | 설명 |
|---|---|---|---|
| `face_interp_speed` | float | **0–40 (기본 20)** | **유지.** 0 = 즉시 스냅 |
| `dead_radius` | float | **15–50 cm (기본 25)** | **유지.** 이 반경 내 커서는 미갱신 |
| `dt` | float | > 0 | 프레임 델타타임 |

**출력 범위:** 항상 [−180°, 180°] 정규화. `dead_radius` 미달 시 미갱신 → atan2 특이점·스냅튐 방지
**예시:** actor=0°, target=90°, speed=20, dt=1/60 → alpha=0.333 → `new_yaw = 30°`. 약 10프레임(166ms)에 수렴 — **아카이브와 동일한 수렴 시간**

**근거 — 재보정하지 않는다:** 이동은 다리(전신 이동, cm/s), 조준은 손(각속도)이다. **서로 다른 물리량**이라 `base_move_speed`가 바뀌었다고 같이 낮출 이유가 없다. 오히려 P2("성장 없이 손기술만이 실력") 하에서 **조준 반응성은 이동속도와 독립적으로 항상 최상급이어야** 한다. 이동이 느려졌다고 조준까지 무뎌지면 § Player Fantasy의 **"몸은 도망치고, 손은 겨눈다"에서 손 쪽이 죽는다.**

### 3. `dash_kinematics` — `RequestDash` 운동학 ⭐ 크로스시스템 (스킬 참조)

`dash_duration = dash_dist / dash_speed`
`dash_pos(t) = dash_start_pos + normalize(dash_dir) × dash_speed × t`, `0 ≤ t ≤ dash_duration`

| 변수 | 타입 | 범위 | 설명 |
|---|---|---|---|
| `dash_dist` | float | **200–800 cm** | **유지** — 공간값 |
| `dash_speed` | float | **450–1360 cm/s** | **변경: 800–2400** |
| `dash_duration` | float | **0.15–0.4 s** | **유지** — 실제 제약은 이 값 |

**출력 범위:** 벽 충돌 시 `dash_dist` 미만 조기 종료 가능 (§ Edge Cases)
**예시:** dist=400, speed=1360 → duration = **0.294s** (범위 내)
반례: dist=200, speed=450 → duration = 0.444s → **0.4 상한 초과. 이 조합은 스킬 설계에서 배제**

> ⚠️ **`dist`·`speed`는 자유 조합이 아니다.** 실제 제약은 `duration`이다. 스킬 설계 시
> (dist, speed) 쌍은 **항상 duration이 0.15~0.4s 안에 들어오도록** 골라야 한다.

**근거:** `dash_speed`는 "base 대비 몇 배로 순간 가속하는가"라는 **base 상대 개념**이다. 기존 800~2400은 base 600 대비 **1.33x~4x**. 340에 절댓값 2400을 그대로 두면 **7x** — 걷기 대비 순간이동에 가까워 서버 검증(공식 7)·카메라 리쉬(공식 4)에 과도한 예외를 요구한다. `2400 × (340/600) = 1360` → **정확히 4x가 재현된다**(1360/340 = 4).
반면 `dash_dist`는 **카메라·층 크기에 종속된 공간값**이고 둘 다 안 바뀌었다. 800cm은 화면 폭(30m)의 27%로 여전히 적정하다. `dash_duration`은 "대시 중 얼마나 무방비인가"라는 판정창 시간값이라 base 무관.

> **부수 효과**: base가 느려져 같은 대시 거리의 체감 이득이 커졌다(200cm ≈ 도보 0.588초 분량).
> P2 하에서 대시 아이템의 가치가 올라가는 **의도된 결과**다.

### 4. `camera_follow_lag` — 카메라 위치 보간

고정 탑다운도 lag이 필요하다. ① 서버 스냅백의 화면 노출 완화 ② 급가감속·대시에 1:1 반응하면 로봇 같은 카메라가 됨 ③ 급방향전환 스냅 멀미 방지.

`cam_pos_new = cam_pos_prev + (player_pos − cam_pos_prev) × clamp(dt × cam_lag_speed, 0, 1)`

리쉬 클램프:
`if |player_pos − cam_pos_new| > cam_max_lag_dist: cam_pos_new = player_pos − normalize(...) × cam_max_lag_dist`

| 변수 | 타입 | 범위 | 설명 |
|---|---|---|---|
| `cam_lag_speed` | float | **5–15 (기본 10)** | **유지** — 프레임당 계수 |
| `cam_max_lag_dist` | float | **170 cm** | **변경: 300 → 170** |

**출력 범위:** 카메라–플레이어 거리 항상 [0, 170 cm]
**예시:** lag_speed=10, dt=1/60 → alpha ≈ 0.167. 170cm 벌어진 상태에서 정지 시 약 13프레임(210ms)에 수렴.
대시(200~800cm) 중에는 항상 즉시 170cm 상한까지 벌어져 클램프가 걸린 채 따라간다.

**근거:** 300cm는 base 600 기준 **"0.5초 분량"**(300/600)으로 설계된 값이었다. 340에 그대로 두면 **0.88초 분량** — 카메라가 눈에 띄게 뒤처진다. 불변 설계 의도는 *거리*가 아니라 **시간 예산 0.5초**이므로 `340 × 0.5 = 170cm`. `cam_lag_speed`는 프레임당 추적 계수라 base 무관 → 유지.

> 리쉬가 작아지며 대시 중 "카메라가 확 밀렸다가 따라잡는" 펀치감이 강해진다. **바람직한 부수효과.**

### 5. `diagonal_input_normalization` — 대각선 입력 정규화

`move_vector = raw_input_vector / max(|raw_input_vector|, 1)`

| 변수 | 타입 | 범위 | 설명 |
|---|---|---|---|
| `raw_input_vector` | Vector2D | 디지털 \|v\|∈[0,√2] · 아날로그 [0,1] | `IA_Move` raw (입력 시스템 제공) |
| `move_vector` | Vector2D | \|v\| ≤ 1 | 정규화 결과. `effective_move_speed`와 곱해 최종 속도 |

**출력 범위:** `|move_vector| ≤ 1` 보장
**예시:** W+D → raw=(1,1), |raw|=1.414 → **(0.707, 0.707)**. 대각선이 단일축을 초과하지 않는다(대각 이속 버그 방지)

**근거:** 순수 입력 벡터 정규화로 `base_move_speed`·전송 주기·카메라 어느 것에도 종속되지 않는다. **그대로 유지.**

### 6. `remote_proxy_replay` — 원격 플레이어 재생 🆕

원격 프록시는 `MOVE_None` + `SetActorLocation(bSweep = false)`로 **재생만** 한다 (Core Rule 11).

#### 6a. 보간

`Alpha = clamp(elapsed / InterpDuration, 0.1, 1)`
`NewLocation = Lerp(InterpStart, Dest, Alpha)`

**새 패킷 도착 시 반드시 리타겟한다:**
```
InterpStart = 현재 렌더링 위치      ← 이전 Dest가 아님
elapsed     = 0
Dest        = 새 위치
```

| 변수 | 타입 | 범위 | 설명 |
|---|---|---|---|
| `packet_interval` | float | const **33.3 ms** (1/30 Hz) | 클라 송신 주기 |
| `InterpDuration` | float | const **66 ms** (2 × packet_interval) | 보간 윈도우 |

**출력 범위:** Alpha ∈ [0.1, 1], 오버슛 없음
**예시:** t=0 패킷(Dest_A) → t=33ms 다음 패킷 → Alpha = 33/66 = **0.5** 지점에서 리타겟.
30Hz로 반복되면 **Alpha가 항상 ~0.5 근방에서 리타겟되는 정상상태**가 되어 매끄러운 등속 이동으로 보인다.
지연 시(t=70ms 도착): Alpha가 1.0으로 클램프돼 Dest_A에 잠깐 정지 후 재개.

**근거:** `InterpDuration`을 packet_interval(33ms)과 같게 두면 **1ms만 밀려도 끊긴다.** 3배 이상(100ms+)이면 항상 뒤처져 보인다. **2배(66ms)** 는 지터를 한 틱 흡수하면서 시각 지연은 한 틱만 추가하는 절충점이며, Source 엔진류 표준(interpolation delay = 1~2× update rate)과 일치한다.
**이 프로젝트는 TCP라 패킷 유실이 없고 지연 변동만 있다.** 유실 대비용 긴 버퍼(3배 이상)는 불필요하다.

#### 6b. 텔레포트 판정

`TELEPORT_THRESHOLD = dash_speed_max × jitter_tolerance_window`

| 변수 | 타입 | 범위 | 설명 |
|---|---|---|---|
| `dash_speed_max` | float | const 1360 cm/s | 공식 3 — 게임 내 최고 합법 순간속도 |
| `jitter_tolerance_window` | float | const 150 ms (≈4.5 × packet_interval) | "정상 지터"로 봐줄 최대 무갱신 시간 |
| `TELEPORT_THRESHOLD` | float | **250 cm** | 이 이상 벌어지면 보간 대신 스냅 |

**출력 범위:** 계산값 `1360 × 0.15 = 204cm`, 여유 포함 **250cm**로 확정
**예시:** 최대속도 대시 중에도 30Hz 정상 갱신이면 **틱당 이동은 `1360 × 0.033 = 45cm`** 에 불과하다. 250cm는 이보다 5배 이상 여유가 있어 정상 대시는 절대 스냅되지 않고, 리조인·강제 배치 같은 실제 텔레포트는 확실히 걸린다.

> ⚠️ **총 대시거리(800cm)와 "패킷 한 번당 이동거리"(45cm)를 혼동하면 임계값이 과도하게 커진다.**
> 실제 위험 구간은 "몇 틱이 밀렸을 때 얼마나 벌어지는가"이므로 `최고속도 × 지터허용시간`으로 계산해야 한다.

#### 6c. 속도·가속도 수동 주입

`FrameVelocity = (Dest − InterpStart) / InterpDuration`

```cpp
GetCharacterMovement()->Velocity = FrameVelocity;
if (FrameVelocity.SizeSquared() > 1.f)                          // Acceleration은 protected
    AddMovementInput(FrameVelocity.GetSafeNormal(), 1.f);       // → CMC가 계산
```

| 변수 | 타입 | 범위 | 설명 |
|---|---|---|---|
| `FrameVelocity` | Vector | 0 ~ 1360×√2 cm/s | 현재 보간 레그의 등속 벡터 |
| `velocity_epsilon` | float | const 1 cm/s (`SizeSquared > 1`) | 이 미만이면 정지 간주, `AddMovementInput` 생략 |

**출력 범위:** 무제한(대시 프록시 포함), 정지 시 정확히 0으로 클램프
**예시:** `Dest − InterpStart = 30cm`, InterpDuration = 66ms → FrameVelocity = **454 cm/s**.
`ABP_Unarmed`의 `ShouldMove = (GroundSpeed > 0.01) AND (GetCurrentAcceleration() != 0)` 를 정확히 만족시킨다.

> 🔴 **필수 엣지케이스**: `elapsed ≥ InterpDuration`인데 새 패킷이 아직 안 왔을 때는
> **`Velocity = 0`으로 명시적으로 덮어쓰고 `AddMovementInput` 호출을 생략**해야 한다.
> 안 하면 마지막 `FrameVelocity`가 남아 **캐릭터가 멈춰 있는데 달리기 애니메이션이 재생된다.**

### 7. `server_speed_validation` — 서버 이동 검증 🆕 🔴 서버 영역

#### 7a. 정상 상태

`Δ거리 ÷ Δ시간 ≤ effective_move_speed(player) × validation_margin`

| 변수 | 타입 | 범위 | 설명 |
|---|---|---|---|
| `Δ거리` | float | ≥ 0 cm | 연속 두 위치 패킷 간 이동거리 |
| `Δ시간` | float | > 0 s | **서버 수신 타임스탬프 실측차.** 1/30 고정 가정 금지 |
| `effective_move_speed(player)` | float | [170, 510] cm/s | 서버가 그 플레이어 장비로 **직접 계산** (공식 1) |
| `validation_margin` | float | const **1.15** | 여유율 |
| `min_delta_t` | float | const 16.6 ms (0.5 × packet_interval) | 이보다 짧은 간격은 검증 제외 (0나눗셈·플러딩 방지) |

**출력 범위:** 통과 / 실패 이진. 실패 시 마지막 유효 위치로 스냅백
**예시:**
- 무버프: 0.0333s에 11.5cm → 345.3 cm/s ≤ `340 × 1.15 = 391` → **통과**
- 이속캡 버프: 0.0333s에 16.8cm → 504.5 cm/s → 상한이 `510 × 1.15 = 586.5` → **통과**

> 🔴 **초안 `340 × 1.15`는 버그였다.** 상수 340을 쓰면 **이속 장비를 낀 플레이어가 정상 이동만으로
> 강제 스냅백당한다**(effective는 최대 510). 서버는 이미 장비 상태의 권위를 가지므로 계산 가능하다.

**근거 — `1.15` 유지:** `Δ시간`을 고정 가정이 아니라 **서버 실측 타임스탬프 차이**로 계산하면 지연 변동 자체가 분모에서 상쇄된다. 남는 오차원은 IOCP 워커 수신 처리 지연(부하 시 수 ms) · CMC 서브스텝 양자화 · 부동소수 정밀도뿐이다.
30Hz로 주기가 짧아지며 패킷당 절대 거리가 작아져(11cm대) **같은 절대 오차가 상대오차로는 더 크게 보인다** — margin을 5Hz 때보다 낮출 근거는 없다.

> **TCP는 순서를 보장한다.** "패킷 재정렬"은 이 아키텍처에 해당 없는 우려다. 실제 변수는 지연의 **크기 변동**뿐이다.

#### 7b. 예외 — 대시 · 넉백: "권위 있는 이동 윈도우"

대시(최대 1360 cm/s)는 정상 상한(최대 586.5)의 2배를 넘는다. **예외가 없으면 대시 자체가 불가능하다.**

```
캐스트 / 이벤트 승인 시:
  player.moveException = {
    maxSpeed  = 이번 캐스트의 실제 dash_speed,     ← 전역 최댓값이 아님
    expiresAt = now + 해당 능력의 duration
  }

검증 시:
  ceiling = (exception 활성?) ? exception.maxSpeed : effective_move_speed(player)
  Δ거리 ÷ Δ시간  ≤  ceiling × 1.15

만료 시:
  최종 위치가 서버 기대 위치(start + dir × dist, 벽충돌 시 단축분 허용) 오차범위 내인지 별도 확인
```

**예시:** dist=800, speed=1360 대시 승인 → duration 0.588s 동안 ceiling = `1360 × 1.15 = 1564 cm/s`.
이 구간의 한 패킷이 `45.3cm / 0.0333s = 1360 cm/s`를 보고 → 1564 이내 → **통과.**
예외 미적용이면 정상 상한의 2배를 넘어 **무조건 거부**됐을 것이다.

**근거:** 대시와 넉백은 성격이 다르지만 **"서버가 이미 그 이동의 파라미터를 알고 승인했다"** 는 공통점이 있어 같은 메커니즘으로 처리하면 코드 중복이 없다. 다만 넉백은 서버가 궤적을 직접 연산하므로(전투 시스템 소유), 속도비 검증 대신 **"서버 계산 기대 위치와의 거리 오차"로 직접 검증**하는 편이 더 정확할 수 있다.
margin은 두 경우 모두 **7a와 동일한 1.15**로 통일한다 — 대시처럼 샘플 수가 적은 구간(4~18패킷)은 오히려 노이즈에 민감하므로 좁힐 이유가 없고, 단일 상수가 튜닝·이해에 단순하다.

> 🔴 **선행 조건 — Dependencies에 반영 필요**: 이 예외가 동작하려면 **스킬 시스템이 대시 실행 *전에*
> 서버에 캐스트를 통지**해 `moveException`을 먼저 등록해야 한다. § Interactions의 `스킬 → RequestDash`
> 경로에는 이 **서버 통지 경로가 빠져 있다.**

## Edge Cases

### 이동 · 페이싱

| 상황 | 처리 | 근거 |
|---|---|---|
| 커서가 캐릭터 위 (`dead_radius` 25cm 내) | 페이싱 미갱신, 직전 yaw 유지 | atan2 특이점·스냅튐 방지 (공식 2) |
| 커서 화면 밖 | 입력이 화면경계 clamp, 이동은 마지막 유효 월드좌표 사용 | 조준 무효화 방지 |
| 커서 아래 지오메트리 없음 (허공·구멍) | `GetHitResultUnderCursor`가 아닌 **캐릭터 Z평면 해석적 교차**로 산출 → 항상 유효 | 허공에서 페이싱 소실 방지 |
| 반대 입력 동시 (W+S / A+D) | 합벡터 0 → `Idle` | 상쇄 정상 |
| 걷다가 벽 충돌 | CMC 벽면 슬라이드 (정지 아님) | 표준 이동감 |
| 두 폰이 같은 공간으로 밀어넣음 | 콜리전 해소, 오버랩 없음 | 겹침 방지 |
| 이속 버프가 상한 초과 | **510 cm/s로 클램프** | 공식 1 하드캡. PvP 공정성 |
| 감속이 하한 미만 | **170 cm/s로 클램프** | 감속이 스턴급이 되는 것 방지 |

### 대시

| 상황 | 처리 | 근거 |
|---|---|---|
| 대시가 벽에 충돌 | 스윕이 벽면에서 정지, **조기 종료**(관통 없음), 잔여거리 취소 | 벽 관통 방지 |
| 대시가 다른 폰에 충돌 | 폰 블로킹 정지(밀치기 없음), 조기 종료 | 폰 관통·강제밀치 방지 |
| 대시 중 **Stun** | 대시 즉시 취소 → `Moving`/`Idle` (잔여 변위 없음) | 하드 CC는 강제이동도 끊는다 |
| 대시 중 **Root** | **진행 중 대시는 유지**(변위 완료), 종료 후 걷기 봉쇄 | Root = 신규 이동 봉쇄이지 기존 변위 취소가 아님 |
| `duration`이 0.15~0.4s 범위 밖인 (dist, speed) 조합 | **스킬 설계 단계에서 배제.** 런타임 검사 아님 | 공식 3 — `duration`이 실제 제약 |

### 네트워크 · 서버 검증

| 상황 | 처리 | 근거 |
|---|---|---|
| **서버 검증 실패** | 서버가 마지막 유효 위치로 **스냅백**. 클라는 그 위치를 권위로 수용 | 공식 7a |
| `Δ시간 < 16.6ms` 인 패킷 | **검증에서 제외**(무시) | 0나눗셈·플러딩 방지 |
| 대시 **예외 윈도우 만료 후** 여전히 고속 | 정상 상한(`effective × 1.15`)으로 복귀 → **거부** | 공식 7b |
| 예외 윈도우 만료 시점의 위치 불일치 | 서버 기대 위치(`start + dir × dist`) 오차범위 검사. 벽충돌 단축분은 허용 | 대시 종료 지점 조작 방지 |
| 🔴 **스킬이 서버 통지 없이 `RequestDash` 호출** | 예외 윈도우가 없어 **정상 상한으로 검증 → 거부.** 대시가 스냅백됨 | **설계 결함이 아니라 순서 위반.** § Dependencies에 통지 경로 필수 |

### 원격 프록시

| 상황 | 처리 | 근거 |
|---|---|---|
| 위치차 > `TELEPORT_THRESHOLD` (250cm) | 보간 없이 **즉시 스냅** + `Velocity = 0` + 보간 상태 리셋 | 공식 6b |
| **다음 패킷 미도착** (`elapsed ≥ InterpDuration`) | 🔴 **`Velocity = 0` 명시적 대입 + `AddMovementInput` 생략** | 안 하면 **멈춘 채로 달리기 애니메이션이 재생된다** |
| 새 패킷 도착 | `InterpStart` = **현재 렌더링 위치**(이전 `Dest` 아님), `elapsed = 0` | 공식 6a. 이전 Dest를 쓰면 튄다 |
| 원격 프록시가 벽에 겹쳐 보임 | **허용.** `bSweep = false`라 프록시는 충돌 판정을 하지 않는다 | 충돌 판정 권위는 조작 주인의 클라 (Core Rule 11) |

### 카메라

| 상황 | 처리 | 근거 |
|---|---|---|
| 서버 스냅백으로 큰 위치 튐 | 카메라 lag이 흡수, `cam_max_lag_dist` 170cm 내로 클램프 | 화면 떨림·멀미 방지 (공식 4) |
| 대형 dt 스파이크 (프레임드랍) | 보간 alpha가 `clamp(0,1)`이라 **오버슛 없음** | 저프레임 안정성 (공식 2·4) |
| 카메라와 플레이어 사이에 벽·건물 | **아무것도 하지 않는다.** `bDoCollisionTest = false` | 카메라가 당겨지면 시야가 요동친다. **레벨 설계로 해결할 문제** (지붕 없는 단층 구조 — `game-concept.md` § 세계관) |
| 대시로 170cm 초과 이격 | 리쉬 클램프 발동, 상한까지 당김 | 공식 4 |

### 외부 권위

| 상황 | 처리 | 근거 |
|---|---|---|
| 넉백·강제이동 (전투) | **외부 속도가 입력 이동에 우선.** 이동은 양보 | 넉백 권위 = 전투 |
| 사망 중 | 이동·페이싱 비활성 | 인벤토리 & 사망 처리 시스템 소유 |
| 진입 직후 3초 무적 | **이동은 관여하지 않는다.** 평소대로 동작 | 무적 = 전투 소유 |

> **아카이브에서 사라진 케이스**: 점프·공중 상태 관련 전부 (Core Rule 5 — 지상 전용).

## Dependencies

| System | 방향 | 성격 | 인터페이스 |
|---|---|---|---|
| **입력 시스템** | 이동 → 의존 | **하드** | `IA_Move` raw 벡터 + 커서 월드좌표. 없으면 이동·페이싱 불가 |
| **네트워킹 & 서버** | ↔ | **하드** | out: 위치·yaw 30Hz / in: 스냅백. **권위 = 서버** |
| **레벨 & 맵** | 이동 → 의존 | **하드** | 콜리전 지오메트리(벽·바닥). 없으면 이동 판정 불가 |
| **전투 시스템** | 전투 → 이동 | **하드** (역방향) | 전투가 `can_move`/`can_turn` 공급. 넉백 등 외부 속도 공급. **CC 저항력 계산은 전투 소유** |
| **스킬 시스템** | 스킬 → 이동 | **하드** (역방향) | 스킬이 `RequestDash(dir, dist, speed)` 호출, 이동이 실행 |
| **스킬 → 서버** | 스킬 → 네트워킹 | 🔴 **하드 · 순서 강제** | **대시 실행 *전에* 서버에 캐스트 통지 → `moveException` 등록.** 없으면 공식 7이 대시를 거부한다 |
| **아이템 & 장비** | 장비 → 이동 | 소프트 | `flat_ms_bonus` · `percent_ms_bonus` 공급 (공식 1) |
| **레이더 시스템** | 레이더 → 이동 | 소프트 | 플레이어 월드좌표·yaw 조회 |
| **HUD** | HUD → 이동 | 소프트 | 플레이어 좌표 (머리 위 마커 앵커) |
| **몬스터 AI** | AI → 이동 | 소프트 | NavMesh 경로이동은 AI 소유. CMC 로코모션 규약만 공유 |

### 🔴 입력 시스템에 요구하는 계약 — 서비스 **2개**로 분리 필요

**아카이브(`design/archive/dungeonking-2026-07/input-system.md`) Rule 4는 "커서→월드 판정"을 `GetHitResultUnderCursor` **단 하나**로 정의한다. 이 GDD는 그것을 명시적으로 배제한다**(§ Edge Cases — 허공·구멍 위에서도 페이싱이 유효해야 함).

이름은 같고("커서 월드좌표 쿼리") 구현이 충돌하므로, **입력 시스템 GDD 작성 시 두 서비스로 분리**해야 한다.

| 서비스 | 구현 | 반환 | 소비처 |
|---|---|---|---|
| **`GetCursorWorldPosition()`** | **캐릭터 Z평면 해석적 교차** | **항상 유효. 실패 없음** | **이동(페이싱)** · 스킬(논타겟 조준) |
| `GetTargetUnderCursor()` | `GetHitResultUnderCursor` 히트테스트 | **null 가능** (대상 없음) | 기본공격 대상 판정 · 타겟형 스킬 |

> **왜 입력 쪽을 고치나**: 입력 시스템은 Foundation 레이어(의존 없음)이고, 이 GDD는 이미 구체 수치
> (`dead_radius` 25cm · `TargetArmLength` 2600)까지 확정한 상위 문서다. **하위가 상위 계약에 맞추는 것이
> 설계 순서상 맞다.** 이 GDD의 § Dependencies 말미에 적어둔 "재확인 필요"가 바로 이 지점이었다.

### 🔴 순서가 강제되는 의존 하나

```
잘못된 순서:  스킬 → RequestDash → 클라 대시 시작 → 서버가 고속 감지 → 거부 → 스냅백
올바른 순서:  스킬 → 서버 캐스트 통지 (moveException 등록)
                   → RequestDash → 클라 대시 → 서버 통과
```

**이것은 "구현 순서 팁"이 아니라 계약이다.** 순서를 어기면 대시가 작동하지 않는다(§ Edge Cases).
**스킬 시스템 GDD 작성 시 이 통지를 스킬 쪽 책임으로 명시해야 한다.**

### 양방향 정합성

**하위 의존 시스템 6개**(전투 · 스킬 · 아이템 & 장비 · 레이더 · HUD · 몬스터 AI)가 **전부 미설계**다. 설계 순서상 이동이 먼저라 정상이지만, 각 GDD 작성 시 **"depends on 이동 & 카메라"를 명시**해야 한다.

> ⚠️ **상위 의존 2개**(입력 시스템 · 네트워킹 & 서버)도 아직 GDD가 없다.
> 이 GDD는 그 인터페이스를 **전제**로 작성되었다 — 두 GDD가 나오면 인터페이스 이름·타입·책임 경계가
> 일치하는지 **재확인이 필요하다.**

## Tuning Knobs

### 이동

| 파라미터 | 기본값 | 안전 범위 | ↑ 높이면 | ↓ 낮추면 |
|---|---|---|---|---|
| `base_move_speed` | **340** cm/s | 300–400 | 층 횡단 빨라짐 · **세션 시간 예산 붕괴** | 느림 · 카이팅 난이도↑ |
| `flat_ms_bonus` 상한 | **85** cm/s | 60–110 | 이속 아이템 1개의 영향력↑ | 이속 아이템 무가치화 |
| `ms_max_ratio` | **1.5** | 1.3–1.8 | 카이팅 강화 · 도주 밸붕 | 추격 쉬움 |
| `ms_min_ratio` | **0.5** | 0.4–0.6 | 감속 약화 | **감속이 스턴급으로 강력** |
| `accel` / `braking` (CMC) | 튜닝 | — | 민첩·즉각 정지 | 관성감·굼뜬 반응 |
| `pawn_collision` | on | bool | 몸싸움·막힘(끼임 가능) | 통과·겹침 허용 |

> 🔴 **`base_move_speed`는 사실상 고정값이다.** 층 크기 280m · 횡단 82초 · 집 간격 37초 ·
> 세션 시간 예산이 **전부 여기서 파생**된다. 바꾸면 `game-concept.md` § 공간 전체를 재계산해야 한다.

### 페이싱

| 파라미터 | 기본값 | 안전 범위 | ↑ | ↓ |
|---|---|---|---|---|
| `face_interp_speed` | **20** | 0–40 | 스냅·정밀 조준 / 부자연 | 부드러움 / **조준 지연 = 손맛 죽음** |
| `dead_radius` | **25** cm | 15–50 | 근접 커서 안정 / 데드존 체감↑ | 민감 / atan2 특이점 위험 |

### 카메라

| 파라미터 | 기본값 | 안전 범위 | ↑ | ↓ |
|---|---|---|---|---|
| `TargetArmLength` | **2,600** | — | 시야↑ / **캐릭터 작아져 판독성↓ · P4 위반** | 시야↓ / 몰입↑ |
| `FieldOfView` | **60°** | 50–75 | 원근감↑ · 왜곡↑ | 납작함↑ · 긴 암 필요 |
| `cam_pitch` | **−60°** | −50 ~ −75 | 순수 탑다운 · **실루엣 판독 손실** | 비스듬 · 원근감↑ |
| `cam_lag_speed` | **10** | 5–15 | 타이트 추적 / 스냅백 노출 | 부드러움 / 놓침 |
| `cam_max_lag_dist` | **170** cm | 120–220 | 느슨 · 대시 시 원경 | 타이트 / 급스냅 |

> ⚠️ **`TargetArmLength`와 `FieldOfView`는 자유 노브가 아니다.** 둘의 조합이 화면 가시 면적을 정하고,
> 그것이 **동시 가시 인원 → 대역폭 → 레이더 반경**으로 연쇄한다.
> 하나만 바꾸면 `game-concept.md` § 공간의 밀도 계산이 깨진다.

### 네트워크

| 파라미터 | 기본값 | 안전 범위 | ↑ | ↓ |
|---|---|---|---|---|
| `MOVE_PACKET_SEND_DELAY` | **1/30** s | 1/20 ~ 1/60 | (주기↑) 대역폭↓ · **원격 움직임 뭉개짐** | 대역폭↑ · 부드러움↑ |
| `InterpDuration` | **66** ms | 50–100 | 지터 흡수↑ / **시각 지연↑** | 반응↑ / **끊김 위험** |
| `TELEPORT_THRESHOLD` | **250** cm | 200–400 | 스냅 덜 발생 / 텔포 핵 허용 | 정상 지연에도 스냅 발생 |
| `validation_margin` | **1.15** | 1.10–1.25 | 관대 / 스피드핵 여지 | 엄격 / **정상 유저 오탐** |
| `jitter_tolerance_window` | **150** ms | 100–250 | `TELEPORT_THRESHOLD` 연동 상승 | 동 하락 |

> **`InterpDuration`은 `MOVE_PACKET_SEND_DELAY`의 2배를 유지해야 한다.**
> 전송 주기를 바꾸면 이 값도 같이 바꿔야 한다 — 독립 노브가 아니다.

### 대시 — 🔴 이 시스템 소유 아님

`dash_dist` · `dash_speed` · `dash_duration`은 **스킬 시스템 소유**다. 공식 3은 계약만 정의한다.
다만 **`dash_speed` 상한 1,360**은 서버 검증 예외 윈도우(공식 7b)의 상한과 연동되므로,
넘기려면 서버 쪽 협의가 필요하다.

> **하드코딩 금지**: 위 모든 노브는 외부 config(`DataAsset` / `DataTable` / `DeveloperSettings`)에서
> 로드한다. 코드 리터럴 금지 — `.claude/docs/coding-standards.md` "게임플레이 값은 데이터 주도".

### 🔑 핵심 원칙 — 검증 로직을 순수 함수로 뽑아라

**공식 1~7의 "수식이 맞는가"는 2클라이언트도 네트워크도 필요 없다.** 검증 함수를
`ValidateMove(deltaDist, deltaTime, effectiveSpeed, margin)` 같은 **순수 함수**로 뽑으면 **GoogleTest 하나로 끝난다.**
DummyClient·2클라는 "그 순수함수가 실제 패킷 파이프라인에 올바르게 연결됐는가"를 보는 **Integration 계층에서만** 필요하다.

이 구분을 하지 않으면 Logic 스토리인데 Integration 수준의 무거운 검증을 요구하게 된다.
